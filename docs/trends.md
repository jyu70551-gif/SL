# 요즘 뜨는 식품 (시연 데이터로 만든 첫 버전)

점주가 최근 관심을 받는 식품을 발견하고, 관련 콘텐츠를 근거로 왜 화제가 됐는지 이해하도록 돕는 탭입니다.
흐름: 관심이 늘어난 식품 확인 → AI 설명 확인 → 원본 콘텐츠 확인 → 관심 식품 저장.
**외부 유행만으로 발주 증량을 권하지 않습니다.** 이번 단계에는 자동 발주도, 우리 점포 상품·매출과의 연결도 없습니다(화면에 연결된 것처럼 보이는 요소도 없습니다).

## 1. 데이터 공급원 확인 (2026-11-03 기준)

프로젝트에 연결된 공급원은 모두 **식품 언급량이 없는** 공공·지도 자료입니다. 새 공급원은 아직 고르지 않았습니다.

| 구분 | 공급원 | 내용 |
|---|---|---|
| **지금 실제로 가져올 수 있는 것** | 카카오 로컬, 공공데이터포털(학교·시장·공휴일), 소상공인 상가정보, NEIS, SGIS, 기상청 | 장소·학교·상가·인구·날씨·공휴일. **식품·SNS 게시물은 없음** |
| 별도 계정·승인·유료 계약이 필요하거나 가능성만 있는 것 | 검색 관심도(예: 포털의 검색어 트렌드 API), 영상·블로그 검색 API, 인스타그램·틱톡의 공식 API | **이번 단계에서는 어느 것도 선택하지 않았고 공식 문서로 확인하지 않았습니다.** 선택하면 먼저 제공 범위·이용 조건·저장 허용 범위를 공식 문서로 확인합니다. 검색 관심도를 쓰게 되면 게시물 언급량과 **별도 지표**로만 보여 줍니다. |
| 지금 확보할 수 없는 것 | 인스타그램·틱톡 전체의 실시간 언급량, 비공개 게시물, 작성자 나이·성별·지역 | 확보할 수 있다고 가정하지 않습니다. 무단 로그인 우회나 비공개 수집은 하지 않습니다. |

그래서 **실제 공급원이 연결되기 전까지는 시연 데이터**로 화면·저장·집계·AI 설명을 완성했습니다.

## 2. 실제 수집과 시연 데이터의 분리

- 실제 수집 코드는 **아직 없습니다.** 새 공급원은 `trend.ingest()`에 같은 모양(원본 ID, 게시 시각, 허용된 글, 링크, 종류, 계정 해시, 재게시·광고 표시)의 목록을 넘기고, 날짜별 수집 상태를 `trend.set_collection()`으로 남기면 됩니다.
- 시연 데이터 공급 코드는 [trend_demo.py](../backend/app/trend_demo.py)로 **따로** 있고, 공급원 이름은 항상 `demo`입니다. 화면은 이 이름을 보고 탭 맨 위에 "시연 데이터 · 지어낸 가짜 게시물이에요. 실제 SNS 언급량이 아니에요"를 표시합니다(실제 공급원이 섞이면 "실제·시연 데이터 섞임").
- 시연 게시물은 모두 지어낸 글이고 앞에 `[시연 데이터]`가 붙으며 **원문 링크가 없습니다**(링크가 없다고 화면에 적습니다). 식품 이름·브랜드도 지어낸 것입니다.
- 시연 서버에는 `backend/tools/load_trend_demo.py --db lab/demo.db`로 넣습니다(`--gap`은 직전 기간에 수집 실패한 날을 둡니다). SQLite `.db` 파일만 대상이라 Supabase에는 쓰지 않습니다. 실제 서버에는 시연 데이터가 들어가지 않습니다.
- 어디에도 API 키·비밀값을 쓰지 않습니다.

## 3. 집계 규칙 (코드가 계산합니다. AI는 숫자를 만들지 않습니다)

[trend.py](../backend/app/trend.py)

- **언급량** = 그 식품을 언급한 **중복 제거 게시물 수**. 같은 게시물이 여러 별칭으로 같은 식품을 언급해도 한 건입니다. 조회수·댓글·좋아요와 섞지 않고, 검색 관심도와도 별개입니다.
- **중복·재게시**: ① 같은 공급원의 같은 원본 ID는 한 번만 저장(DB 제약). ② 같은 계정의 같은 글(복사·중복 수집)은 `계정 + 정리한 글`이 같아서 한 건. ③ 재게시로 표시된 것은 세지 않음. ④ **공식 발표는 게시물 수에 세지 않고** 근거로만 씁니다. 계정을 모르면 글이 같아도 합치지 않습니다.
- **식품·별칭**: 식품마다 이름, 브랜드, 별칭, 종류(식품 유형 / 개별 상품)를 둡니다. 같은 별칭이 둘 이상의 식품에 걸리면(동명·다른 브랜드의 유사 상품) **자동으로 연결하지 않고** 어느 쪽에도 세지 않습니다.
- **기간**: 한국 시간(KST) 기준 "최근 완료된 7일"(어제까지)과 그 직전 7일을 비교합니다. 공급원이 다른 기간을 줄 경우의 처리는 공급원을 붙일 때 정합니다(지금은 시연 데이터라 해당 없음).
- **증가량** = 현재 − 이전, **증가율** = 증가량 ÷ 이전 × 100. 이전 기간이 0건이면 증가율을 계산하지 않고 "새롭게 관측됨"으로 표시합니다.
- **수집 상태**: 공급원·날짜별로 `ok` / `failed`를 저장하고, 행이 없으면 "미수집"입니다. **미수집·실패는 0건이 아니라 "모름"**이고 일별 추이 그래프에서도 선이 끊깁니다. 어느 기간이든 `ok`가 아닌 날이 있거나 두 기간의 수집 범위(scope)가 다르면 **비교하지 않고 증가 순위에서 뺍니다**(이유 표시). 언급량순 목록은 일부만 수집됐다는 경고와 함께 남깁니다.
- **순위**: 관심 증가순 = **증가량**이 큰 순서(같으면 증가율). 증가율로 줄 세우면 2건에서 8건 같은 작은 숫자가 상위를 독점하기 때문입니다. 언급량순 = 현재 기간 게시물 수.
- **작은 표본 걸러내기(검증 전 초기값, 제 판단)**: 현재 기간 게시물 10건 미만, 또는 작성 계정 수를 아는데 5곳 미만이면 증가 순위에서 뺍니다(이유 표시). 값은 `trend.PARAMS`에서 바꿉니다.
- **플랫폼별**: 공급원(source)을 콘텐츠마다 보존하고 집계에 `by_source`로 함께 담습니다.
- **광고·협찬**: 콘텐츠에 광고·협찬 표시(`is_ad`)가 있는 경우에만 표시하고, 게시물 수에는 포함한 채 "광고·협찬 표시 N건 포함"을 알립니다.
- **작성 계정 수**: 계정 해시를 아는 경우에만 세고, 모르면 "확인하지 못했어요"로 표시합니다.
- **썸네일**: 이미지 사용 권한이 확보된 공급원이 없어서 보여 주지 않습니다.

## 4. AI 설명

[trend_ai.py](../backend/app/trend_ai.py) · 프롬프트 버전 `trend-1`

- AI에는 허용된 글(식품별 최근 콘텐츠), 게시 날짜, 공식 발표 여부, 광고 표시와 코드가 계산한 지표만 보냅니다. **링크 주소와 계정은 보내지 않습니다.**
- 설명은 세 항목: **확인된 계기**(공식 발표에서 확인한 사실만) / **자주 등장하는 내용**(수집한 글에서 반복된 주제, "게시물에서 언급됐어요") / **해석**("~일 수 있어요", 원인 단정 금지). 각 항목은 근거 콘텐츠 번호를 달고, 홈에는 핵심 한두 문장(`summary`)만 보입니다.
- 검사: 근거 번호가 실제 근거에 있어야 하고, 확인된 계기는 공식 발표만 근거로 쓸 수 있으며, 인과 단정("~ 때문에", "~ 덕분")·근거에 없는 연령·성별 표현("10대", "학생" 등)·근거에 없는 숫자·발주를 권하는 말·링크/서식이 있으면 거절하고 한 번만 이유를 알려 다시 시킵니다.
- 쓸 만한 글(본문 15자 이상)이 3건 미만이면 AI를 부르지 않고 "관심이 늘어난 이유를 설명할 자료가 부족해요"를 표시합니다. 링크나 해시태그뿐인 콘텐츠로는 설명을 만들지 않습니다.
- 캐시: 같은 근거·지표 지문이면 저장한 설명을 씁니다(`trend_explanations`). 근거나 지표가 바뀌면 "설명이 오래됐을 수 있어요"를 알리고, 점주가 다시 만들 수 있습니다. 실패한 것은 캐시하지 않고 다시 시도할 수 있습니다.
- AI가 실패하거나 꺼져 있어도 집계·원문(근거 콘텐츠) 목록·저장은 그대로 동작합니다.
- 한계: 숫자·번호·단정 표현은 코드가 검사하지만 **의미까지 검사하지는 못합니다.** 외부 글에 섞인 지시문은 데이터로만 취급하도록 지시했을 뿐 완전히 막는 장치는 아닙니다.

## 5. 저장 구조 (마이그레이션 0012, 표 6개)

| 표 | 내용 |
|---|---|
| `trend_foods` | 식품: 이름, 브랜드, 별칭(JSON), 종류 |
| `trend_contents` | 콘텐츠: 공급원, 원본 ID(공급원과 함께 유일), 종류(게시물/공식 발표), URL, 게시 시각(UTC), 수집 시각, 허용된 글, 계정 해시, 중복 열쇠, 재게시·광고 표시 |
| `trend_mentions` | 식품–콘텐츠 연결(식품 번호, 콘텐츠 번호) |
| `trend_collections` | 공급원·한국 날짜별 수집 상태(ok/failed)와 수집 범위, 수집 시각 |
| `trend_explanations` | AI 설명: 식품, 기간, 근거 지문, 쓴 근거 ID, 생성 시각, 모델, 프롬프트 버전, 상태, 설명 |
| `trend_favorites` | 관심 식품(사용자가 한 명이라 식품 번호와 저장 시각) |

**기간별 집계 표는 따로 두지 않습니다.** 게시물 수·계정 수는 저장된 콘텐츠에서 읽을 때마다 계산해서(같은 값을 두 곳에 두지 않으려고) 낡을 일이 없고, 수집 상태만 `trend_collections`에 남깁니다. 원본 콘텐츠의 저장·보존 범위는 실제 공급원의 이용 조건을 따라야 하며, 지금은 시연 데이터라 해당 없습니다.

## 6. 주소

`GET /api/trends`(요약·순위) · `GET /api/trends/foods/{id}/evidence`(근거 콘텐츠) · `GET|POST /api/trends/foods/{id}/explanation`(저장된 설명 / 만들기, `refresh`) · `POST|DELETE /api/trends/favorites/{id}`(관심 식품). 모두 비밀번호 통행증이 있어야 합니다.

## 8. 실제 수집을 연결하려면 (남은 조건)

1. 공급원 선택 + **공식 문서로 제공 범위·이용 조건(저장·재배포·이미지 사용) 확인**, 필요한 계정·승인·유료 계약 확보.
2. 그 공급원의 수집 코드(식품별 검색어·해시태그, 날짜별 수집 상태 기록)와 이용 조건에 맞는 보존 범위 정하기. 수집 범위가 바뀌면 `scope`를 바꿔 기록(비교가 자동으로 막힘).
3. 기준값(7일, 10건, 5곳)과 별칭 목록을 실제 자료로 점검.
4. 우리 점포 상품·매출과의 연결은 별도 설계(이번 단계에는 없음).
