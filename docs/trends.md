# 요즘 뜨는 식품

> **현재 화면은 11장("오늘 보기")입니다.** 2~8장은 처음 만든 "시연 데이터 + 14일 비교 증가 순위 + AI 설명" 방식의 설계이고, 9장은 그 방식을 실제 데이터로 돌려 보려던 Apify 수집입니다. **그 코드(`trend.py`, `trend_ai.py`, `trend_demo.py`, 14일 수집 도구, 옛 주소, 표 6개)는 2026-11-04에 모두 지웠습니다**(표는 마이그레이션 0013이 지움). 2~10장은 설계 기록으로만 남깁니다. 11장이 그 한계 때문에 바꾼 현재 방식입니다. 변천 과정: [feature-history/10-trends.md](feature-history/10-trends.md)

점주가 최근 관심을 받는 식품을 발견하고, 관련 콘텐츠를 근거로 왜 화제가 됐는지 이해하도록 돕는 탭입니다.
흐름: 관심이 늘어난 식품 확인 → AI 설명 확인 → 원본 콘텐츠 확인 → 관심 식품 저장.
**외부 유행만으로 발주 증량을 권하지 않습니다.** 이번 단계에는 자동 발주도, 우리 점포 상품·매출과의 연결도 없습니다(화면에 연결된 것처럼 보이는 요소도 없습니다).

## 1. 데이터 공급원 확인 (2026-11-03 기준)

프로젝트에 연결된 공급원은 모두 **식품 언급량이 없는** 공공·지도 자료입니다. 새 공급원은 아직 고르지 않았습니다.

| 구분 | 공급원 | 내용 |
|---|---|---|
| **지금 실제로 가져올 수 있는 것** | 카카오 로컬, 공공데이터포털(학교·시장·공휴일), 소상공인 상가정보, NEIS, SGIS, 기상청 | 장소·학교·상가·인구·날씨·공휴일. **식품·SNS 게시물은 없음** |
| 별도 계정·승인·유료 계약이 필요하거나 가능성만 있는 것 | 검색 관심도(예: 포털의 검색어 트렌드 API), 영상·블로그 검색 API, 인스타그램·틱톡의 공식 API | **이번 단계에서는 어느 것도 선택하지 않았고 공식 문서로 확인하지 않았습니다.** 선택하면 먼저 제공 범위·이용 조건·저장 허용 범위를 공식 문서로 확인합니다. 검색 관심도를 쓰게 되면 게시물 언급량과 **별도 지표**로만 보여 줍니다. |
| 지금 확보할 수 없는 것 | 인스타그램·틱톡 전체의 실시간 언급량, 비공개 게시물, 작성자 나이·성별·지역 | 확보할 수 있다고 가정하지 않습니다. 무단 로그인 우회나 비공개 수집은 하지 않습니다. |

### 1-1. 네이버 검색 API(블로그·카페글) 확인 결과 (2026-11-03, 사용 설명서만 읽음)

공식 사용 설명서(api.ncloud-docs.com, 2026-09-17 갱신)에서 확인한 것:
- 블로그 검색: `query`, `display`(1~100), `start`(1~**1000**), `sort`(정확도 `sim` / 날짜 `date`). **날짜 범위 필터는 없습니다.** 응답은 `total`(전체 검색 결과 수), `items`(제목, 링크, 요약 `description`, 블로거 이름, `postdate`(날짜))입니다. 요약만 주고 본문은 주지 않습니다.
- 하루 호출 한도 25,000회라는 문구가 있고, 같은 사이트의 FAQ에는 "검색 카테고리 월 최대 775,000건", "API Key당 최대 50 RPS"도 있어서 단위가 다릅니다(어느 쪽이 맞는지 미확인). 한시적 무료이고 유료 전환 시 공지한다고 합니다.
- 카페글 검색도 같은 한도의 별도 API가 있습니다.

그에 따른 기술적 한계: `total`은 기간과 무관한 **전체 개수**라서 "최근 7일 게시물 수"로 쓸 수 없습니다. `sort=date`로 최신부터 `start` 1000까지(최대 약 1,100건) 넘기며 `postdate`로 기간을 직접 세야 하고, 일주일에 1,000건이 넘는 식품은 끝까지 셀 수 없어서 "수집 게시물 기준(상한 있음)"으로만 쓸 수 있습니다.

**확인하지 못한 것(중요):** 검색 API 특약의 저장·캐싱, 보관 기간, AI 입력·학습, 통계·집계 용도, 제3자 제공, 출처 표시, 광고·수익화, 개정 시행일. 개발자센터(developers.naver.com)는 이 환경에서 읽을 수 없었고, 읽을 수 있었던 네이버 클라우드 문서 어디에도 약관 본문이 없었습니다. 개정 약관이 저장·캐싱·AI 입력을 금지한다는 내용은 **뉴스 보도로만** 보았고 공식 확인이 안 됐습니다. 약관 원문은 API 허브 이용 신청 화면의 "이용 약관 및 개인정보 제공 안내"에서 확인할 수 있어 보입니다.

그래서 **실제 공급원이 연결되기 전까지는 시연 데이터**로 화면·저장·집계·AI 설명을 완성했습니다.

## 2. 실제 수집과 시연 데이터의 분리

- 실제 수집 코드는 **인스타그램 해시태그(Apify) 한 가지만** 있습니다(아래 9장). 다른 공급원은 없습니다. 새 공급원은 `trend.ingest()`에 같은 모양(원본 ID, 게시 시각, 허용된 글, 링크, 종류, 계정 해시, 재게시·광고 표시)의 목록을 넘기고, 날짜별 수집 상태를 `trend.set_collection()`으로 남기면 됩니다.
- 시연 데이터 공급 코드는 `trend_demo.py`(삭제됨)로 **따로** 있고, 공급원 이름은 항상 `demo`입니다. 화면은 이 이름을 보고 탭 맨 위에 "시연 데이터 · 지어낸 가짜 게시물이에요. 실제 SNS 언급량이 아니에요"를 표시합니다(실제 공급원이 섞이면 "실제·시연 데이터 섞임").
- 시연 게시물은 모두 지어낸 글이고 앞에 `[시연 데이터]`가 붙으며 **원문 링크가 없습니다**(링크가 없다고 화면에 적습니다). 식품 이름·브랜드도 지어낸 것입니다.
- (삭제됨) 시연 서버에는 `backend/tools/load_trend_demo.py --db lab/demo.db`로 넣었습니다(`--gap`은 직전 기간에 수집 실패한 날을 둡니다). SQLite `.db` 파일만 대상이라 Supabase에는 쓰지 않습니다. 실제 서버에는 시연 데이터가 들어가지 않습니다.
- 어디에도 API 키·비밀값을 쓰지 않습니다.

## 3. 집계 규칙 (코드가 계산합니다. AI는 숫자를 만들지 않습니다)

`trend.py`(삭제됨)

- **언급량** = 그 식품을 언급한 **중복 제거 게시물 수**. 같은 게시물이 여러 별칭으로 같은 식품을 언급해도 한 건입니다. 조회수·댓글·좋아요와 섞지 않고, 검색 관심도와도 별개입니다.
- **중복·재게시**: ① 같은 공급원의 같은 원본 ID는 한 번만 저장(DB 제약). ② 같은 계정의 같은 글(복사·중복 수집)은 `계정 + 정리한 글`이 같아서 한 건. ③ 재게시로 표시된 것은 세지 않음. ④ **공식 발표는 게시물 수에 세지 않고** 근거로만 씁니다. 계정을 모르면 글이 같아도 합치지 않습니다.
- **식품·별칭**: 식품마다 이름, 브랜드, 별칭, 종류(식품 유형 / 개별 상품)를 둡니다. 같은 별칭이 둘 이상의 식품에 걸리면(동명·다른 브랜드의 유사 상품) **자동으로 연결하지 않고** 어느 쪽에도 세지 않습니다.
- **기간**: 한국 시간(KST) 기준 "최근 완료된 7일"(어제까지)과 그 직전 7일을 비교합니다. 공급원이 다른 기간을 줄 경우의 처리는 공급원을 붙일 때 정합니다(지금은 시연 데이터라 해당 없음).
- **증가량** = 현재 − 이전, **증가율** = 증가량 ÷ 이전 × 100. 이전 기간이 0건이면 증가율을 계산하지 않고 "새롭게 관측됨"으로 표시합니다.
- **수집 상태**: 공급원·날짜별로 `ok` / `failed`를 저장하고, 행이 없으면 "미수집"입니다. **미수집·실패는 0건이 아니라 "모름"**이고 일별 추이 그래프에서도 선이 끊깁니다. 어느 기간이든 `ok`가 아닌 날이 있거나 두 기간의 수집 범위(scope)가 다르면 **비교하지 않고 증가 순위에서 뺍니다**(이유 표시). 언급량순 목록은 일부만 수집됐다는 경고와 함께 남깁니다.
- **순위**: 관심 증가순 = **증가량**이 큰 순서(같으면 증가율). 증가율로 줄 세우면 2건에서 8건 같은 작은 숫자가 상위를 독점하기 때문입니다. 언급량순 = 현재 기간 게시물 수.
- **작은 표본 걸러내기(검증 전 초기값, 제 판단)**: 현재 기간 게시물 10건 미만, 또는 작성 계정 수를 아는데 5곳 미만이면 증가 순위에서 뺍니다(이유 표시). 값은 `trend.PARAMS`에서 바꿉니다.
- **플랫폼별**: 공급원(source)을 콘텐츠마다 보존하고 집계에 `by_source`로 함께 담습니다.
- **광고·협찬**: 콘텐츠에 광고·협찬 표시(`is_ad`)가 있는 경우에만 표시하고, 게시물 수에는 포함한 채 "광고·협찬 표시 N건 포함"을 알립니다.
- **작성 계정 수**: 계정 해시를 아는 경우에만 세고, 모르면 "확인하지 못했어요"로 표시합니다.
- **썸네일**: 이미지 사용 권한이 확보된 공급원이 없어서 보여 주지 않습니다.

## 4. AI 설명

`trend_ai.py`(삭제됨) · 프롬프트 버전 `trend-1`

- AI에는 허용된 글(식품별 최근 콘텐츠), 게시 날짜, 공식 발표 여부, 광고 표시와 코드가 계산한 지표만 보냅니다. **링크 주소와 계정은 보내지 않습니다.**
- 설명은 세 항목: **확인된 계기**(공식 발표에서 확인한 사실만) / **자주 등장하는 내용**(수집한 글에서 반복된 주제, "게시물에서 언급됐어요") / **해석**("~일 수 있어요", 원인 단정 금지). 각 항목은 근거 콘텐츠 번호를 달고, 홈에는 핵심 한두 문장(`summary`)만 보입니다.
- 검사: 근거 번호가 실제 근거에 있어야 하고, 확인된 계기는 공식 발표만 근거로 쓸 수 있으며, 인과 단정("~ 때문에", "~ 덕분")·근거에 없는 연령·성별 표현("10대", "학생" 등)·근거에 없는 숫자·발주를 권하는 말·링크/서식이 있으면 거절하고 한 번만 이유를 알려 다시 시킵니다.
- 쓸 만한 글(본문 15자 이상)이 3건 미만이면 AI를 부르지 않고 "관심이 늘어난 이유를 설명할 자료가 부족해요"를 표시합니다. 링크나 해시태그뿐인 콘텐츠로는 설명을 만들지 않습니다.
- 캐시: 같은 근거·지표 지문이면 저장한 설명을 씁니다(`trend_explanations`). 근거나 지표가 바뀌면 "설명이 오래됐을 수 있어요"를 알리고, 점주가 다시 만들 수 있습니다. 실패한 것은 캐시하지 않고 다시 시도할 수 있습니다.
- AI가 실패하거나 꺼져 있어도 집계·원문(근거 콘텐츠) 목록·저장은 그대로 동작합니다.
- 한계: 숫자·번호·단정 표현은 코드가 검사하지만 **의미까지 검사하지는 못합니다.** 외부 글에 섞인 지시문은 데이터로만 취급하도록 지시했을 뿐 완전히 막는 장치는 아닙니다.

## 5. 저장 구조 (마이그레이션 0012가 만들고 0013이 지운 표 6개 — 옛 방식)

| 표 | 내용 |
|---|---|
| `trend_foods` | 식품: 이름, 브랜드, 별칭(JSON), 종류 |
| `trend_contents` | 콘텐츠: 공급원, 원본 ID(공급원과 함께 유일), 종류(게시물/공식 발표), URL, 게시 시각(UTC), 수집 시각, 허용된 글, 계정 해시, 중복 열쇠, 재게시·광고 표시 |
| `trend_mentions` | 식품–콘텐츠 연결(식품 번호, 콘텐츠 번호) |
| `trend_collections` | 공급원·한국 날짜별 수집 상태(ok/failed)와 수집 범위, 수집 시각 |
| `trend_explanations` | AI 설명: 식품, 기간, 근거 지문, 쓴 근거 ID, 생성 시각, 모델, 프롬프트 버전, 상태, 설명 |
| `trend_favorites` | 관심 식품(사용자가 한 명이라 식품 번호와 저장 시각) |

**기간별 집계 표는 따로 두지 않습니다.** 게시물 수·계정 수는 저장된 콘텐츠에서 읽을 때마다 계산해서(같은 값을 두 곳에 두지 않으려고) 낡을 일이 없고, 수집 상태만 `trend_collections`에 남깁니다. 원본 콘텐츠의 저장·보존 범위는 실제 공급원의 이용 조건을 따라야 하며, 지금은 시연 데이터라 해당 없습니다.

## 6. 주소

`GET /api/trends`(요약·순위) · `GET /api/trends/foods/{id}/evidence`(근거 콘텐츠) · `GET|POST /api/trends/foods/{id}/explanation`(저장된 설명 / 만들기, `refresh`) · `POST|DELETE /api/trends/favorites/{id}`(관심 식품). 모두 비밀번호 통행증이 있어야 합니다.

- "근거 콘텐츠 보기"를 열면 AI의 세 항목(근거 번호 포함)과 근거 목록(공식 발표 먼저, 광고·협찬 표시, 링크가 있으면 원문 링크).
- 맨 아래에 "외부 관심만으로 발주를 정하지 마세요. 이 탭은 우리 점포의 상품·매출과 아직 연결돼 있지 않아요."

## 9. 인스타그램 공개 게시물 제한 수집 (Apify, 2026-11-03)

[trend_apify.py](../backend/app/trend_apify.py)(지금은 호출·한도만 남음) · 실행 도구 `collect_instagram_trends.py`(삭제됨) · 공급원 이름 `instagram_apify`(화면에 "실제 수집 데이터"로 표시됨)

### 9-1. 확인한 것 (Apify 공식 페이지)
- 공식 Actor `apify/instagram-hashtag-scraper`: 해시태그 목록, 결과 종류(게시물/릴스), 해시태그당 결과 수를 입력하고, **최신 게시물**을 줍니다(인기순 아님). 입력에 로그인·쿠키 칸은 없습니다. 공개 데이터만 모은다고 안내합니다.
- 결과 필드: 게시물 번호(`shortCode`), 링크, 캡션, 해시태그, 게시 시각(`timestamp`), 작성 계정(`ownerUsername`·`ownerId`), 좋아요·댓글 수 등. **날짜 범위 조건은 없습니다.**
- 가격: 결과당 과금. 무료 플랜 **1,000건에 2.60달러**($5 무료 크레딧 ≈ 2,000건), 페이지 맨 위에는 "1.90달러부터"라고도 적혀 있어 서로 다릅니다(등급별 가격은 가격 탭에서 확인해야 함). 무료 사용은 첫 페이지 결과만이라는 문구도 있습니다.
- API: `POST /v2/actors/apify~instagram-hashtag-scraper/run-sync-get-dataset-items`, 토큰은 `Authorization: Bearer` 머리글(권장), 300초를 넘으면 408, `maxItems`·`maxTotalChargeUsd`로 개수·비용을 막을 수 있습니다.

### 9-2. 먼저 알아 둘 위험 (확인하지 못한 것 포함)
- **Instagram(Meta) 이용약관은 이 페이지들에서 확인하지 못했습니다.** Apify 글은 "웹사이트는 약관으로 수집을 계약상 제한할 수 있다"고 밝히고 "법률 자문이 아니다"라고 적습니다. 자동 수집이 약관 위반일 수 있고, 그 책임은 사용자에게 있다고 보고 진행해야 합니다.
- 공개 게시물이라도 **계정은 개인정보가 될 수 있습니다**(GDPR 등). 그래서 이 코드는 계정 이름을 저장하지 않고 **해시한 값**만 저장합니다.
- 이 수집은 **SNS 전체 언급량이 아닙니다.** 해시태그를 단 최신 게시물 일부이고, 사진·영상 위주라 캡션이 짧거나 해시태그뿐인 게시물이 많습니다.

### 9-3. 제한 (모두 `.env`로 바꿀 수 있음)
| 설정 | 기본값 | 뜻 |
|---|---|---|
| `APIFY_TOKEN` | (없음) | `backend/.env`에만 적습니다. 채팅·문서·로그에는 나오지 않습니다 |
| `APIFY_RESULTS_PER_HASHTAG` | 30 | 해시태그당 받는 최대 게시물 수 |
| `APIFY_MAX_HASHTAGS` | 8 | (삭제됨) 옛 방식이 쓰던 해시태그 수 한도 |
| `APIFY_RUN_MAX_USD` | 0.25 | 한 번 실행 최대 비용(Apify의 `maxTotalChargeUsd`) |
| `APIFY_MONTHLY_RESULTS` | 1500 | 이번 달 받은 결과가 이 수를 넘을 것 같으면 실행하지 않음 |

- 해시태그는 점주가 지정한 식품의 이름·별칭(공백 없이)만 씁니다. 공개 게시물만, 로그인·쿠키 없이 모읍니다.
- 저장은 최소한만: 게시물 번호, 링크, 게시 시각, **캡션 앞 200자**, 계정 해시. 계정 이름·이미지·좋아요·댓글 수는 저장하지 않고, **30일이 지나면 지웁니다**. 광고·협찬 표시는 알 수 없어서 하지 않습니다.
- 한 번 실행하면 돈이 듭니다(예: 해시태그 2개 × 30건 = 최대 60건 ≈ 0.16달러). 도구는 `--dry-run`으로 해시태그·최대 건수·어림 비용을 먼저 보여 주고, 실제 호출은 `--yes`를 줘야만 합니다. 토큰이 없으면 호출하지 않습니다.

### 9-4. 수집한 날의 '모름' 처리 (중요한 한계)
Actor는 최신 게시물을 해시태그당 limit건까지만 주기 때문에 **하루를 온전히 모았는지**를 직접 따집니다. 오늘(T) 실행하면 어제(T-1)를 모읍니다.
- 상한에 닿은 해시태그의 가장 오래된 게시물이 어제 0시보다 늦으면, 어제 앞부분을 못 본 것이라 어제는 **`capped`(상한에 걸려 일부만 수집)** 로 기록합니다. 0건이 아니라 '모름'이라서 비교와 증가 순위에서 빠지고 화면에 이유가 나옵니다.
- 어제보다 더 이전 날은 **모든 해시태그가 상한까지 거슬러 올라간 경우에만** 확인된 것으로 칩니다(그렇지 않으면 없던 날을 있다고 하게 되어서).
- 그래서 **하루 게시물이 limit보다 많은 인기 해시태그는 거의 항상 `capped`** 라 순위가 나오지 않습니다. 이 방식은 하루 게시물이 limit(기본 30)보다 적은 **작은 해시태그**에만 맞습니다. 비교가 성립하려면 같은 식품·해시태그·상한으로 **14일 연속**(최근 7일 + 직전 7일) 매일 한 번씩 실행해야 합니다. 해시태그나 상한을 바꾸면 수집 범위가 달라져 비교가 막힙니다.

### 9-5. 쓰는 법
1. `backend/.env`에 `APIFY_TOKEN=`을 직접 채웁니다(채팅에 붙여 넣지 마세요). 필요하면 제한값도 바꿉니다.
2. (삭제된 도구) 계획만 보기: `backend\.venv\Scripts\python.exe tools\collect_instagram_trends.py --db lab/demo.db --food "식품이름=별칭,별칭" --dry-run`
3. 실제로 모으기: 같은 명령에서 `--dry-run` 대신 `--yes`. 하루에 한 번.
4. (삭제된 도구) 실제 서버(Supabase)에 쓰려면 `--db` 대신 `--supabase`(먼저 `alembic upgrade head`로 0012까지 적용). **저는 이 도구를 실행하지 않았습니다.** 토큰이 없어서 실제 Apify는 한 번도 호출해 보지 않았고, 시험은 가짜 응답으로만 했습니다.
5. 시연 서버의 가짜 식품과 같은 DB에 넣으면 `실제·시연 데이터 섞임`으로 표시됩니다.

### 9-6. 점주가 아무것도 하지 않는 자동 모드 (2026-11-03)

식품 이름이나 해시태그를 점주가 고르지 않아도 되게 `--auto`를 더했습니다([trend_discover.py](../backend/app/trend_discover.py)).
1. **발견**: 기본 해시태그 `#편의점신상 #편의점디저트 #편의점간식`의 최근 게시물 캡션에서 AI가 **상품 이름 후보**만 뽑습니다. 개수·순위는 코드가 세고 AI는 숫자를 만들지 않습니다.
2. **코드가 검사**: 이름이 근거 게시물 캡션에 **글자 그대로** 있어야 하고(띄어쓰기는 무시), **서로 다른 게시물 2건·계정 2곳 이상**이어야 하며, 브랜드(GS25, CU 등)와 일반 이름(도시락, 젤리 등)은 뺍니다. 별칭도 캡션에 실제로 있는 것만 받습니다.
3. **자동 추적**: 통과한 후보를 식품으로 등록해 추적 목록에 올리고, 이후 그 식품 **자신의 해시태그**로 게시물을 모아 순위를 셉니다. 추적 해시태그 한도(기본 8개)가 차면 발견은 건너뜁니다.
4. 발견용 게시물(`instagram_discovery`)은 상한에 거의 항상 걸려 일부만 본 것이라 **순위 계산에 세지 않습니다.**
5. 추적 해시태그 집합이 바뀌면 수집 범위가 달라진 것으로 보고 비교를 막습니다(새로 추적한 식품은 앞날의 자료가 없어서). 그래서 **새 식품을 추적하기 시작한 뒤 14일 동안은 그 범위의 증가 순위가 나오지 않습니다.**

한계(실제로 돌려 보고 확인한 것): 23건의 게시물에서 후보가 2개(피자설기 3건·계정 3곳, 요즘블루베리그릭요거트모찌롤 2건·계정 2곳)만 나왔습니다. 후보가 적고, 한 번에 모으는 게시물이 적어서 **순위가 나오려면 14일 연속 매일 실행**해야 하며, 인기 해시태그는 상한에 걸려 '모름'이 됩니다. **자동 실행(스케줄)은 아직 없습니다**: 지금은 `--auto --yes`를 사람이 하루에 한 번 돌려야 합니다. 매일 자동으로 돌리면 월 비용이 계속 나가서(예: 해시태그 8개 × 30건 ≈ 하루 0.6달러, 한 달 약 19달러) 월 비용 상한을 먼저 정해야 합니다.

## 11. 오늘 보기 (버튼 한 번, 비교 없음) — 화면의 현재 방식

점주가 매일 수집하게 하지 않으려고 화면을 바꿨습니다. **14일 비교·증가 순위·관심 식품 저장·AI 설명 화면은 쓰지 않습니다**(2~8장의 집계 코드와 `/api/trends` 옛 주소는 2026-11-04에 지웠습니다).

- 버튼 "오늘 트렌드 가져오기": `#편의점신상 #편의점디저트 #편의점간식` 최근 게시물을 해시태그당 30건(최대 90건) 한 번 받습니다. 약 0.2달러.
- AI 는 캡션에서 상품 이름 후보만 뽑고, **건수는 코드가 전체 게시물에서 다시 셉니다.** 서로 다른 게시물 2건·계정 2곳 이상인 이름만 보입니다. 순서는 게시물 수 → 계정 수.
- **하루 1회**: 오늘 이미 받았으면 저장된 결과를 보여 주고 다시 부르지 않습니다. 월 한도(1,500건)와 실행 비용 상한(0.25달러), AI 가 꺼져 있으면 **게시물을 받기 전에** 막아 비용이 들지 않습니다.
- **회수·안전 글은 순위에서 빼고 접힌 주의 영역(절제된 앰버, 빨강 아님)으로 따로 보여 줍니다.** 가려내는 것은 AI 가 아니라 고정 단어 목록(회수, 판매중단, 부적합, 검출, 리콜, 이물질, 식중독, 대장균, 섭취중단 등. 띄어쓰기 무시)입니다. '폐기'·'환불'은 폐기 할인 같은 일반 글에 쓰여서 뺐습니다. 펼치면 게시물 앞 80자 발췌·게시일·원본 링크·(알아본 경우) 상품 이름이 나오고(최대 5건), **게시물이 한 말일 뿐 공식 확인이 아니라고** 적습니다. 단어 목록은 검증 전이라 쿠폰 회수 같은 글이 걸리거나 다른 표현을 놓칠 수 있고, 캡션을 앞 200자만 저장해서 뒤쪽 내용은 못 봅니다. 식약처 공개 정보 연결은 이용 조건을 확인하지 않아 하지 않았습니다.
- 저장: 상품 이름·건수, 근거 게시물(앞 80자 발췌·게시일·링크) 상품당 최대 5건, 주의 게시물 최대 5건, 게시물 기간(`AppSetting` 한 줄, 새 테이블 없음 → Supabase 마이그레이션 불필요). 게시물 본문 전체는 저장하지 않고, 이름 찾기는 전체 글(안전 글 포함)로 하되 건수는 안전 글을 뺀 것만 셉니다.
- 한 게시물에 상품이 여러 개 나오면 각 상품에 1건씩 셉니다(단독/함께 구분은 하지 않음). 총정리 글이 있으면 건수가 같이 오를 수 있습니다.
- 화면 문구: "최근 게시물에서 많이 언급된". **검색량도, 증가 추세도 아닙니다.** 표본(90건) 안에서의 순서일 뿐 편의점 전체 인기가 아닙니다.
- 한계: 표본이 작아 순위가 흔들릴 수 있습니다. AI 가 상품이 아닌 이름을 뽑을 수 있어 목록(BRANDS/GENERIC)으로 일부만 거릅니다. 이름 후보가 하나도 없으면 그날은 빈 결과로 저장되어 내일까지 다시 못 받습니다.

### 11-1. 화면 구조 (2026-11-04 개편)
위에서부터 ① 제목·짧은 설명 ② 갱신 상태(마지막 갱신 시각·수집 게시물 수·"인스타그램 실제 수집") + 버튼 ③ 식품 카드(2열, 모바일 1열. 순위 번호 없음, 건수 많은 순) ④ 접힌 "안전 관련 언급 · 확인 필요 게시물 N건"(절제된 앰버, 빨강 아님) ⑤ 접힌 "수집 기준과 한계 보기".
- 버튼: 가능하면 "최신 식품 살펴보기", 수집 중 "가져오는 중…", 오늘 끝났으면 버튼 대신 "✓ 오늘 수집 완료 · 다음 수집은 내일", 실패하면 이유와 "다시 시도".
- 카드의 "근거 게시물 N건 보기"를 펼치면 게시물 발췌(앞 80자, 이모지 제거)·게시일·원본 링크(상품당 최대 5건)가 나옵니다. "게시물에 쓰인 말이고 확인된 사실이 아니다"라고 적습니다.
- **AI 요약 문장은 이 화면에 없습니다**(상품별 AI 설명을 만들지 않으므로 영역을 생략). 이미지·썸네일도 쓰지 않습니다(사용 권한 미확인).
- **미구현**: 식약처 등 공식 출처 연결과 "공식 확인" 표시, 공식 확인된 긴급 정보의 상단 별도 표시. 안전 관련 언급은 전부 "공식 확인 전"으로만 보여 줍니다.
- 수집 기준 영역에는 플랫폼·해시태그·게시물 기간(받은 글의 게시일 범위)·수집 시각·사용 게시물 수·집계 방식·수집 한도·한계가 모여 있고, 사용량은 카드 위에 나열하지 않습니다.

### 11-2. 안전 표시와 옛 코드 정리 (2026-11-04)
- **목록의 상품에도 안전 표시를 붙입니다.** 안전 글을 가려내는 것은 단어 목록이라 단어가 없는 관련 글은 식품 목록에 남을 수 있는데, 같은 상품 이름이 들어 있는 안전 글이 있으면 그 식품 카드에 앰버 안내("이 상품은 안전 관련 언급이 있어요(게시물 N건). 위 건수에는 세지 않았어요. 아래 '안전 관련 언급'에서 확인하고, 공식 공지도 확인해 주세요")를 붙입니다(`safety_posts`). 건수를 빼거나 순위를 바꾸지는 않습니다. **한계:** 단어 목록에 걸리지 않은 관련 글은 이 표시에도 잡히지 않습니다. 이전에 저장된 결과에는 이 값이 없어 표시가 보이지 않습니다.
- **옛 방식의 코드를 지웠습니다:** 14일 비교 집계(`trend.py`), AI 설명(`trend_ai.py`), 시연 데이터 공급(`trend_demo.py`), `/api/trends` 옛 주소 5개(식품 요약·근거·설명·관심 식품), 14일 수집·자동 추적 도구와 시험, 표 6개(마이그레이션 0013이 지움. 0012는 그대로 두었고 0013이 이어서 지웁니다), 화면의 옛 CSS. `trend_apify.py`에는 호출·한도·월 사용량·결과 변환만, `trend_discover.py`에는 상품 이름 후보 검증만 남겼습니다.
