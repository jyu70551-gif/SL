# 내일 예상 매출(Phase 7) 고려사항

> 첫 버전을 만들었습니다(6장). 확인한 사실과, 점주가 정한 방침, 보류한 항목을 모아 둔 곳입니다.
> 통계 방법을 만들면 [stats-guide.md](stats-guide.md)에 쉬운 말로 설명을 더합니다.

## 1. 자료의 한계 (먼저 알아야 할 것)

- 실제 매출은 **월·화·수 23일뿐**입니다. 목·금·토·일은 한 번도 본 적이 없어서, 실제 자료만으로는 내일이 목요일 이후일 때 예상을 만들 수 없습니다.
- 23일에는 설 연휴도 섞여 있습니다. 요일, 장날, 연휴, 날씨의 계수를 믿을 만하게 추정하기에는 자료가 모자랍니다.
- 시연 DB는 실제 23일의 분포로 만든 가짜 자료이고 날씨 효과가 들어 있지 않습니다. 시연 DB에서 날씨 효과를 "발견"하면 지어낸 결과입니다. 시연 DB로는 **코드가 맞게 동작하는지**만 확인할 수 있습니다. (날씨 효과를 일부러 심은 별도 가짜 자료로 모형이 그 효과를 찾아내는지 보는 방법을 쓸 수 있습니다)
- 따라서 **"정확하다"고 말하는 화면은 만들지 않습니다.** 서비스 성격은 시연·포트폴리오이면서, 실제 점주가 계속 쓴다는 가정으로 만듭니다.

## 2. 모형 방침 (점주와 합의한 방향)

- 매출에 로그를 취하고 요일, 장날, 공휴일, 방학, 기온, 비 온 날을 넣는 **규제 회귀(릿지)**를 씁니다. 자료가 적을 때 계수를 0쪽으로 당겨 우연한 값이 커지는 것을 막고, 결과를 "비가 오면 약 -8%"처럼 설명할 수 있습니다. 부스팅 같은 복잡한 모형은 이 자료 크기에서 득이 없다고 봅니다.
- **지금의 "같은 요일 중간값"보다 나을 때만 모형을 씁니다.** 과거 날들을 하나씩 예측해 보는 검증(백테스트)으로 비교하고, 못하면 기존 기준에 넓은 범위를 붙여 "참고용"으로만 보여 줍니다. 요일 자료가 부족하면 "자료가 부족해요"라고 안내합니다.
- 예측값 하나가 아니라 **가운데 값과 범위**(과거 오차로 계산)를 보여 줍니다. 날씨를 못 받으면 "날씨 빠짐"을 표시합니다.
- 같은 요일 비교에서 장날·공휴일을 어떻게 다룰지(6-3에서 미룬 일)도 여기서 함께 검토합니다.

## 3. 날씨 변수

| 변수 | 출처 | 모형에서 |
|---|---|---|
| 평균 기온 | 기상청 ASOS 일자료(과거 관측) / 단기예보(내일 예측) | 계수 추정 |
| 비 온 날 (일 강수량 1mm 이상) | 같음 | 계수 추정 |

- 습도, 풍속 등은 넣지 않습니다. 자료가 쌓인 뒤 모형 점검 결과를 보고 추가를 검토합니다.
- **학습은 실제 관측값으로, 내일 예측에는 예보값으로** 합니다. 단기예보는 과거 예보 기록을 주지 않기 때문입니다. 예보가 틀리면 예상도 틀어지므로 범위를 넓게 잡는 이유가 됩니다.

### 확인한 기상청 서비스 (공공데이터포털, 키는 서비스마다 따로)

- **과거 날씨: 기상청 지상(종관, ASOS) 일자료** — 키 이름 `WEATHER_PAST_API_KEY`. 평균·최저·최고 기온, 일 강수량(mm), 평균 풍속, 평균 습도, 일조시간 등. 실제 매출이 시작된 2025년 5월 자료부터 어제 자료까지 받아집니다.
  - 시흥에는 관측소가 없습니다. 서울(108), 인천(112), 수원(119), 강화(201), 양평(202)은 확인했고 관악산(116)은 이 서비스에 없습니다. 점포 위치로 가장 가까운 곳을 고르고, 어느 관측소인지 화면에 밝힙니다. (시흥에서 모두 20km 안팎)
  - 같은 날도 관측소끼리 강수량이 꽤 다릅니다. (예: 2026-11-01 수원 12.3mm, 서울 6.5mm, 인천 6.1mm) 날씨 계수에는 이 잡음이 섞인다는 점을 문서에 밝힙니다.
- **내일 예보: 기상청 단기예보(동네예보)** — 키 이름 `WEATHER_FORECAST_API_KEY`. 점포 위치를 격자 번호(nx, ny)로 바꿔 요청하고, 오늘부터 4일 뒤까지 시간별 기온(TMP), 최저·최고 기온(TMN, TMX), 강수확률(POP), 강수량(PCP), 하늘 상태(SKY), 습도(REH), 풍속(WSD)이 옵니다.
- (API허브 형식의 주소로는 위 두 키가 모두 거절됩니다. 공공데이터포털 형식으로만 씁니다.)

## 4. 기상특보 — 보류 (점주 결정: 앱에는 넣지 않고 고려사항으로만 기록)

점주가 폭염, 폭설, 폭우, 태풍 같은 기상특보도 따로 다뤄야 한다고 했고, **가운데 값은 바꾸지 않으며 앱에는 넣지 않고 이 문서에 고려사항으로만 남기기로 했습니다.**

### 확인한 사실 (기상청 기상특보 조회서비스, 키 이름 `WEATHER_WARNING_API_KEY`)

- **과거 특보는 조회되지 않습니다.** 오늘 기준 최근 6일까지만 줍니다. 더 먼 날짜를 요청하면 "최대 조회 기간은 6일 이내"라는 오류가 납니다. 그래서 지금은 **모형 학습에 쓸 수 없습니다.**
- 현재 발효 중인 특보는 알 수 있습니다. 통보문(`getWthrWrnMsg`)의 "현재 발효 중인 특보 현황"에 종류별로 구역 목록이 글로 나옵니다. 예: `한파주의보 : 경기도(가평, 군포, 이천, …)`. 이 구역 목록에 "시흥"이 들어 있는지로 해당 여부를 판단할 수 있습니다.
- 종류(강풍, 한파, 호우, 대설, 폭염, 태풍, 풍랑 등), 주의보·경보 구분, 발표·해제, 해제 예고 시각이 글에 들어 있습니다. 바다 특보(풍랑 등)는 점포와 상관이 없습니다.
- 한계: 구역 이름이 글로 적혀 있어 글 모양이 바뀌면 못 읽을 수 있습니다.

### 나중에 다룬다면 (제안, 아직 결정하지 않음)

1. **가운데 값은 바꾸지 않습니다.** 특보의 효과를 아는 자료가 없기 때문입니다. (점주 결정)
2. 시흥이 구역에 확실히 적힌 특보가 있을 때만, 예상 범위를 넓히고 "○○ 발효 중이라 예상이 불확실해요"를 붙이는 방법을 검토합니다. 경보는 주의보보다 더 넓힙니다. 구역을 못 읽으면 적용하지 않고 "확인 못 함"으로 보여 줍니다.
3. 발효 중인 특보를 매일 저장해 두면 몇 달 뒤 학습 자료가 됩니다. 종류별로 발효된 날이 충분히 쌓이면(예: 5일 이상) 모형 변수로 넣을지 검토합니다. 그 전에는 변수에 넣지 않습니다.
4. 지금 실제 자료(1~2월 23일)에는 폭염·폭우·태풍 특보가 없었고, 있었더라도 한두 번뿐이라 계수를 만들 수 없습니다.

## 5. 아직 정하지 않은 것

- Phase 7을 시작하는 시점과, 시연 DB에 날씨를 어떻게 채울지 (시연 DB의 날짜에 맞는 실제 ASOS 값을 넣을지, 가짜로 만들지)
- 점주에게 보이는 카드의 모양과 문구 ("참고용" 표시, 범위 표현)
- 같은 요일 비교에서 장날·공휴일 처리 방식

## 6. 첫 버전 구현 결과 (2026-11-02)

- **만든 것**: 날씨 저장(`weather_daily`, 마이그레이션 0010), 설정 화면 "과거 날씨 가져오기", 회귀 모형(릿지) + 걸러서 맞혀 보기 + 최근 오차 보정, 홈 "내일 예상 매출" 카드. 계산 방법은 [stats-guide.md](stats-guide.md) 3장, 화면은 [spec.md](spec.md) 7-8·7-9.
- **방침대로 정한 것**: 모형이 평소 기준보다 낫다고 확인될 때만 모형을 씁니다. 범위는 과거 오차로 만듭니다. 기상특보는 쓰지 않습니다. 시연 DB는 "실제 관측 날씨 + 가정한 날씨 효과를 심은 가짜 매출"이고, 모형이 심은 값을 되찾는지로 코드를 확인합니다.
- **실제 23일의 결과**: 모형이 낫다고 확인되지 않아 평소 기준을 씁니다. 목요일은 본 적이 없어 안내가 붙습니다.
- **정정**: 2~3장의 탐색을 처음 돌릴 때 매출 파일의 "합계" 줄을 하루 매출에 한 번 더 더해 금액이 2배로 나왔습니다. 비율 결과는 그대로이고 금액만 틀렸습니다. 앱은 합계 줄을 올바르게 뺍니다.
- **남은 것**: (1) 자료가 쌓이면 최근 오차 보정(14일·절반)과 기준(5%)을 다시 점검(7·8장). (2) 같은 요일 비교에서 장날·공휴일을 어떻게 다룰지(지금은 모형의 장날·공휴일·방학 변수로만 반영). (3) 기상특보. (4) 날씨 변수 추가(습도·풍속) 검토.

## 7. 지금 선택한 모형과 선택하지 않은 것 (2026-11-02)

### 선택한 것
**릿지(L2) 회귀 + 최근 오차 보정(최근 14일 오차의 절반) + "평소 기준보다 나을 때만 사용" 안전장치.** 범위는 과거 오차의 10%/90% 지점으로 만들고, 화면에는 범위만 보여 줍니다. 식과 계산 과정은 [stats-guide.md](stats-guide.md) 3장에 있습니다.

### 왜 이것인가 (시드가 다른 시연 자료 3개, 최근 45일 걸러서 맞히기, 평균)
| 비교 | 결과 | 판단 |
|---|---|---|
| 보정 있음 / 없음 | 평균 오차 28.7% / 31.9%, 범위점수 1.24 / 1.31 | **보정을 넣는다.** 보정 없이는 모형이 평소 기준보다 나빠 쓰이지 않음 |
| 보정 크기 절반 / 전부 | 28.7% / 26.7% (3주 제외 26.2% / 26.6%) | **절반 유지.** 전부는 일부러 넣은 상황이 있는 구간에서만 좋고, 수준이 안 변하는 가게에서는 우연한 흔들림을 따라갈 위험 |
| 날씨 포함 / 뺌 (보정 절반) | 28.7% / 31.3% | 날씨는 오차를 약 2.6%p 줄임. 크지 않지만 도움이 됨 |
| L1 라쏘, 엘라스틱넷 | 28.7%, 범위점수 1.25 | 성능이 같고 변수를 0으로 지워 설명이 불안정하므로 **L2 유지** |
| 강건 회귀(Huber) | 28.4%, 보통의 날 20.3%(릿지 22.3%), 범위 더 넓음 | 평균은 같고 범위가 넓어져 **바꾸지 않음** |
| 그래디언트 부스팅, 랜덤 포레스트, ARIMAX | 30.2~30.9%, 범위점수 1.30~1.33 | 더 복잡하지만 낫지 않아 **선택하지 않음** |
| Holt-Winters (날씨·달력 없음) | 30.2%, 범위점수 1.17(가장 좋음) | 평균 오차는 릿지보다 크고 장날·공휴일·날씨를 설명할 수 없어 **선택하지 않음** |
| 릿지 + 최근값 특징(전날·7일·14일 평균) | 30.6% | 보정만 넣은 릿지보다 낫지 않음 |

- 모형끼리의 차이는 대부분 1~2%p로 우연의 범위 안입니다. 일부러 넣은 상황 3주를 빼면 거의 모두 25.7~28.5%이고, 이 자료의 하루 흔들림이 커서(로그 표준편차 약 0.3) 약 25%가 줄일 수 없는 바닥입니다.
- 개선의 대부분은 날씨가 아니라 **보정(수준 변화 추적)**에서 나옵니다.
- **한계**: 시연 자료는 로그에서 곱셈으로 작용하는 선형 효과를 심어 만들어서 **선형 회귀가 구조적으로 유리**합니다. 실제 점포에서는 비선형 모형이 나을 수도 있지만 지금 자료로는 알 수 없습니다. 평가한 날이 자료당 35일이라 작은 차이는 우연입니다. 실제 23일에서는 비교 자체가 안 됩니다.
- (비교 실험은 임시 환경에서 돌렸고 프로젝트에는 들어 있지 않습니다. 필요하면 같은 방식으로 다시 돌릴 수 있습니다.)

### 지금은 하지 않기로 한 것 (재검토 시점)
| 항목 | 이유 | 다시 볼 때 |
|---|---|---|
| 보정 전부 반영 | 이 자료에서는 낫지만 일반화 근거 부족 | 점주 자료가 수 개월 쌓였을 때 같은 비교로 |
| 범위 폭 넓히기 | 범위 안에 들어온 비율이 77%로 목표 80%보다 약간 낮음(범위가 조금 좁음). 폭을 5~10% 넓히는 것을 검토 | 실제 자료로 범위 적중률을 잴 수 있을 때 |
| 다른 모형(부스팅, 상태공간 등) | 이길 근거가 없음 | 실제 자료가 훨씬 늘어난 뒤 같은 백테스트로 |

## 8. 실제 자료가 늘면 쓸 수 있는 식 (고려사항)

같은 백테스트와 "평소 기준보다 나을 때만 사용" 안전장치를 그대로 쓰고, 이길 때만 바꿉니다.

### ① 같은 틀에서 항을 늘리는 방향
```
로그(매출) = 상수 + 요일 7개 + 계절 + 기온(비선형) + 비(양) + 휴일 종류 + 방학×요일 + 장날×요일
           + 특보 + 행사 + 전날·최근 7일 수준 + 오차
```
| 추가할 항 | 필요한 자료 | 이유 |
|---|---|---|
| 계절 (연간 주기를 사인·코사인으로) | 최소 1년, 두 해면 확실 | 방학·기온·연휴가 겨울에 몰려서 분리하려면 한 해 이상 필요 |
| 기온 비선형 (더운 날·추운 날, 또는 제곱항) | 여름·겨울 모두 | 25도 이상, 0도 이하에서 효과가 다를 수 있음 |
| 비의 양(로그 강수량), 눈, 전날 비 | 비 온 날 30일 이상 | 지금은 비 온 날이 3일뿐 |
| 휴일 종류 (설·추석 연휴, 단일 휴일, 연휴 전후) | 연휴 2~3회 | 지금은 설 연휴 3일뿐 |
| 방학×요일, 장날×요일 | 요일당 수십 번 (1.5배 차이를 알아채려면 약 32주) | 평일과 주말에 효과가 다를 수 있음 |
| 기상특보 (폭염·한파·호우·대설·태풍) | 종류별 5일 이상 발효된 기록 | 과거 특보를 조회할 수 없어서 매일 저장해 모아야 함 (4장) |
| 행사·판촉 | 점주의 "행사" 기록이 쌓이면 | 이상한 날을 학습에서 빼거나 변수로 넣음 |
| 최근 수준 (전날, 최근 7일 평균) | 지금도 가능 | "최근 오차 보정"을 정식 항으로 바꿈 |

### ② 범위를 더 정확하게
- **분위수 회귀**: 오차의 10%/90% 지점을 요일·상황별로 직접 추정합니다. 지금은 모든 날의 오차를 한데 모아 같은 폭을 쓰는데, 주말이나 연휴처럼 흔들림이 다른 날을 구분할 수 있게 됩니다.
- **공형 예측(conformal)**: 과거 오차로 "정말 80%가 들어온다"는 보장을 맞춥니다. 자료가 수백 일 되면 가능합니다.

### ③ 다른 모형 후보 (자료가 훨씬 많아진 뒤)
| 후보 | 어떤 때 | 비고 |
|---|---|---|
| 그래디언트 부스팅, 랜덤 포레스트 | 비선형 상호작용이 클 때 (예: 더운 주말에만 급증) | 이번 비교에서는 이기지 못함. 시연 자료가 선형이라 불리했다는 한계 |

| 분류별 모형 | 분류별 데이터가 충분할 때 | 합산해서 총매출 범위를 냄 |

### ④ 현실적인 로드맵
1. **약 3~6개월**: 요일 7개와 장날, 공휴일, 비를 안정적으로 추정할 수 있습니다. 최근 오차 보정을 정식 항으로 바꾸는 시점입니다.
2. **약 1년**: 계절 항을 넣어 방학과 기온 효과를 분리하고, 휴일 종류를 세분합니다.
3. **그 뒤**: 특보 변수, 분위수 회귀, 비선형 모형을 같은 백테스트로 비교해 이길 때만 바꿉니다.

## 9. 시연 자료에 공휴일·방학이 없는 이유와 고치는 방법 (아직 안 함)

- `--demo`는 공휴일 효과를 일부러 끕니다(`no_holidays`). 처음 만들 때 앱에 휴일 정보를 쓰는 곳이 없었고, 탐지가 휴일을 건너뛰지 않아 휴일에 가짜 알림이 늘기 때문이었습니다. 지금은 앱에 공휴일 가져오기와 "참고" 문구가 있어서 이유가 약해졌지만, 탐지는 여전히 휴일을 건너뛰지 않습니다.
- 시연 자료를 만드는 도구에는 **방학 효과가 아예 없습니다.** 실제 자료로 알 수 없어서 가정조차 하지 않았습니다.
- 앱의 "공휴일 가져오기"는 올해와 내년만 저장해서 시연 기간(2025-05~2026-02)의 2025년 휴일은 저장되지 않습니다.
- **고친다면**: ① 시연 기간의 실제 공휴일을 특일 정보에서 받아 시연 DB에 저장하고 가정한 효과(단일 휴일 −15%, 설·추석 연휴 −55%)를 반영 ② 근처 학교의 실제 방학을 저장하고 가정한 방학 효과를 반영(방향과 크기는 근거가 없는 가정이라 표시 필요). 휴일에 탐지의 가짜 알림이 늘어나는 부작용도 함께 확인해야 합니다.
