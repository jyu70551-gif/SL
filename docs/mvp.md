# SL MVP 기획서

> MVP란 "처음 세상에 내놓는 가장 작은 버전"입니다.
> 이 문서는 SL의 첫 버전에서 **무엇을 만들고, 무엇은 일부러 미루는지**를 정리합니다.

---

## 1. SL은 어떤 서비스인가요?

**SL은 편의점 점주를 위한 "하루 매출 정리 도우미"입니다.**

매일 상가 프로그램에서 뽑은 매출 파일을 올리면, SL이 다음 일을 대신 해줍니다.

- 오늘 얼마나 팔렸는지 한눈에 정리해 줍니다.
- 평소와 너무 다르게 팔린 항목을 찾아서 "이건 한번 확인해 보세요"라고 알려줍니다.
- 삼각김밥, 햄버거 같은 즉석식품이 평소 어느 정도 팔리는지 보여줘서 발주(주문) 때 감을 잡도록 돕습니다.
- 내일 매출이 대략 어느 정도일지 예상 범위를 보여줍니다.

### 왜 만드나요?

즉석식품은 오래 보관할 수 없어서 발주가 어렵습니다. 너무 많이 시키면 버리게 되고, 너무 적게 시키면 못 팔게 됩니다. SL은 통계와 AI의 도움으로 이 **"얼마나 시켜야 할지 모르겠는" 불확실함을 줄이는 것**을 목표로 합니다.

---

## 2. 누가 쓰나요?

- **첫 사용자는 한 명, 점포도 한 곳입니다.** (시흥시 거모동 주택가, 시장과 장날이 있는 골목 근처)
- 그래서 첫 버전에는 로그인도, 여러 점포를 관리하는 기능도 없습니다. 아주 단순하게 시작합니다.
- 주로 **마감 후 스마트폰**으로 확인한다고 가정합니다.
- **인터넷에 올려서** 어디서나 접속하고, 다른 사람이 못 보도록 **간단한 비밀번호 하나**를 둡니다.

---

## 3. 첫 버전(MVP)에서 만들 것

### 3-1. 데이터 올리기

- 매일 한 번, 상가 프로그램에서 뽑은 **CSV 파일**(엑셀처럼 표로 된 파일)을 올립니다. 열은 PDF와 같습니다: 상품코드, 대분류, 판매수량, 판매액, 연도, 달, 일, 요일
- 올릴 때 **"몇 시까지의 매출인지"** 시각을 직접 입력합니다.
- 올린 데이터는 계속 쌓입니다.
- 같은 날짜의 파일을 다시 올리면 **새 파일로 덮어쓰고**, 덮어쓰기 전에 확인 창을 띄웁니다.
- 나중에는 포스기(계산대)와 직접 연결해서 자동으로 가져오는 것이 목표입니다. 첫 버전은 파일 올리기만 합니다. 다만 나중에 자동 연결을 붙이기 쉽도록 구조는 열어 둡니다.

### 3-2. 초기 화면 (카드형, 폰에서 한눈에)

위에서 아래로 카드가 쌓인 모양입니다.

| 순서 | 카드 | 보여주는 내용 |
|---|---|---|
| 1 | **확인이 필요한 대분류** | 평소와 크게 다르게 팔린 항목과, AI가 쓴 이유 설명 |
| 2 | **오늘 총매출·판매수량** | 오늘 합계, 같은 요일과의 비교 |
| 3 | **즉석식품 요약** | 간편식사·즉석조리의 오늘 판매량과 평소 범위 비교 |
| 4 | **내일 예상 매출** | 내일 매출이 어느 정도일지 예상 범위 |

> 모든 카드에는 **"몇 시까지의 매출인지"** 를 표시합니다.
> 데이터를 근무가 끝날 때쯤 뽑기 때문에, 하루 전체가 아닐 수 있기 때문입니다.

> **데이터가 아직 적은 동안**에는 같은 요일 비교, 이상치, 예상 매출 카드가 자리를 유지한 채 **"데이터가 더 필요해요"** 안내와 진행 상황을 보여줍니다.

화면은 폰 하단 메뉴로 **홈 / 파일 올리기 / 설정(방학 날짜 입력)** 세 곳을 오갑니다. 대분류 그래프는 홈에서 항목을 누르면 열립니다.

### 3-3. "확인이 필요한 대분류" 카드 (이 서비스의 핵심)

1. **대분류별 매출을 날짜 순서로 그립니다.** (시계열 그래프)
2. **통계로 "평소와 너무 다른 날"을 찾습니다.** 같은 요일끼리 비교해서 크게 벗어나면 후보로 올립니다. 통계적 근거가 있는 방법을 쓰고, 거의 늘 0인 대분류는 따로 처리합니다. (구체적인 계산법은 설계 단계에서 확정합니다)
3. **AI(OpenAI)가 이유를 설명합니다.** 숫자로 된 근거를 먼저 말하고, 원인은 "~일 수 있습니다"라는 **가능성**으로만 말합니다.
   - 예시: "담배가 같은 요일 평소의 3배입니다. 대량 구매 또는 입력 오류일 수 있습니다."
4. 항목을 누르면 그 대분류의 그래프가 열리고, 이상한 날이 표시됩니다.
5. 항목마다 **"확인함·정상"** 이라고 답할 수 있습니다. 답한 항목은 목록에서 사라지고 다시 경고로 뜨지 않으며, 카드 안 링크의 "확인한 항목" 보기에서 **취소**할 수 있습니다.

**왜 AI가 직접 찾지 않고 통계로 먼저 찾나요?**
AI에게 맡기면 같은 데이터인데 결과가 달라질 수 있습니다. 찾는 일은 통계가, 설명하는 일은 AI가 맡아야 믿을 수 있습니다.

**AI는 원인을 단정하지 않습니다.** 실제 이유를 모르는 채로 "단체 주문 때문입니다"라고 말하면 틀릴 수 있기 때문입니다.

### 3-4. 내일 예상 매출

매출에 영향을 주는 요소를 넣은 **회귀모형**으로 예상 **범위와 가운데 값**을 계산합니다. (예: "약 12만 원, 범위 10~14만 원") 구체적인 모형은 설계 단계에서 확정합니다.

고려하는 요소는 다음과 같습니다.

- 요일
- **장날** (5일장: 3, 8, 13, 18, 23, 28일)
- 날씨 (기상청 공공 데이터, 시흥시 기준)
- 방학 여부 (점주가 시작·끝 날짜를 설정 화면에서 직접 입력)
- **명절·공휴일** (공공 데이터. 2026년 설 연휴 때 매출이 크게 줄어든 것이 확인되어 추가했습니다.)

**중요:** 지금은 데이터가 적어서 이 예상은 **"참고용"** 입니다. 화면에도 그렇게 표시합니다.

## 4. 지금 가진 데이터와 한계

### 가지고 있는 것

> 아래 PDF 자료는 **참고용**입니다. SL의 데이터는 PDF를 넣지 않고, **새로 올리는 CSV부터 쌓습니다.**

- 기간: 2025년 12월 23일 ~ 2026년 2월 25일 중 **23일 치**
- 날짜가 연속이 아니라 군데군데 비어 있습니다. (일주일에 1~2일 정도)
- 하루마다 **대분류 24개**(간편식사, 즉석조리, 음료, 담배 등)의 판매수량과 판매액이 있습니다.

### 없는 것 (그래서 생기는 한계)

| 없는 것 | 그래서 어떻게 되나요? |
|---|---|
| **상품별 판매 내역** | "참치마요 삼각김밥" 같은 개별 상품은 볼 수 없습니다. 즉석식품은 **'간편식사'와 '즉석조리' 대분류 기준**으로만 봅니다. |
| **발주량·폐기량 기록** | "많이 팔린 날"과 "재고가 없어 못 판 날"을 구분할 수 없습니다. 그래서 "정확한 발주 추천"이 아니라 **"이 요일에 보통 이만큼 팔렸다"는 범위**를 보여주는 수준입니다. |
| **충분한 기간** | 요일 패턴은 볼 수 있지만, 계절·방학 효과는 믿기 어렵습니다. 장날 효과도 맛보기 수준입니다. |

### 지금 데이터에서 눈에 띈 점 (참고)

- 장날로 보이는 날(1/13, 1/28, 2/3, 2/23)은 평균 매출이 **약 17.6만 원**으로, 그 외 평일(설 연휴 제외) **약 11.8만 원**보다 높았습니다. 차이의 대부분은 담배였습니다.
- 설 연휴(2/16~2/18)에는 매출이 크게 줄었습니다.
- 표본이 작아서 "그럴 가능성이 있다"는 정도로만 봅니다.

## 5. 첫 버전에서 일부러 하지 않는 것

욕심을 줄여야 빨리, 제대로 만들 수 있습니다. 다음은 **뒤로 미룹니다.**

- 로그인, 여러 점포 지원
- 포스기 자동 연동
- 상품 하나하나 단위의 분석과 정확한 발주 추천
- 발주량·폐기량을 직접 입력하는 기능
- 담배를 뺀 매출 같은 보조 지표
- 지금 가진 PDF 자료를 SL에 넣는 일 (참고만 합니다)

## 6. 기술 구성과 폴더 구성

### 쓰는 기술

| 부분 | 기술 | 쉬운 설명 |
|---|---|---|
| 화면 | **React** | 폰에서 보는 카드형 웹 페이지를 만드는 도구 |
| 서버 | **FastAPI** (Python) | 파일 읽기, 이상치 찾기, 예측, AI 설명 요청을 맡는 계산 담당 |
| 데이터 보관 | **Supabase** | 인터넷에 있는 데이터 보관함. 올린 매출 데이터가 여기에 쌓입니다. |
| 테스트용 보관 | **SQLite** | 내 컴퓨터 안의 파일 하나짜리 보관함. 개발하고 시험할 때만 씁니다. |

- 개발 중에는 **SQLite**로 시험하고, 실제로 쓸 때는 **Supabase**를 씁니다. 두 곳에서 **똑같이 동작**해야 합니다.
- 화면과 서버는 서로 분리되어 있어서, 나중에 스마트폰 앱으로 확장하더라도 같은 서버를 그대로 쓸 수 있습니다.

### 폴더 구성

프로젝트에는 이미 네 개의 폴더가 만들어져 있습니다.

| 폴더 | 역할 |
|---|---|
| `frontend` | 사용자가 보는 **화면** (React, 폰에서 보는 카드형 웹 페이지) |
| `backend` | 뒤에서 일하는 **계산 담당** (FastAPI: 파일 읽기, 이상치 찾기, 예측, AI 설명 요청) |
| `database` | 데이터 보관함의 **구조 설명과 설정** (Supabase와 테스트용 SQLite에 만들 표의 모양) |
| `docs` | **문서** (이 파일 등) |

## 7. 만드는 순서 (제안)

한 번에 다 만들지 않고, **쓸 수 있는 상태를 빨리 만든 뒤 하나씩 더합니다.**

1. **접속과 비밀번호:** 인터넷 주소로 열리고 비밀번호를 입력하는 화면을 만듭니다.
2. **데이터 올리기:** CSV 파일과 시각을 입력해 올리고, 쌓이게 만듭니다. (같은 날짜는 덮어쓰기 확인)
3. **오늘 매출 카드:** 총매출, 판매수량, 같은 요일과의 비교를 먼저 보여줍니다. (데이터가 적을 때는 "더 필요해요" 안내)
4. **즉석식품 요약 카드:** 간편식사·즉석조리의 평소 범위와 비교합니다.
5. **확인이 필요한 대분류 카드:** 이상치 찾기 + 그래프 + AI 설명 + "확인함·정상" 처리를 붙입니다.
6. **내일 예상 매출 카드:** 요일·장날·명절 등으로 예상 범위를 보여줍니다. (날씨와 방학은 그다음에 더합니다.)
7. **설정 화면:** 방학 날짜를 입력합니다.
8. **다듬기:** 폰 화면에서 보기 편하게 정리합니다.

## 9. 이 MVP가 성공했다고 볼 기준

- 마감 후 파일을 올리면 **1분 안에** 카드들이 채워진 화면이 보입니다.
- 평소와 다른 날이 있으면 "확인이 필요한 대분류"에 올라오고, 이유가 **알아듣기 쉬운 말로** 설명됩니다.
- 즉석식품 발주를 할 때 "평소 이 요일에 이 정도 팔렸구나" 하는 **참고 자료**가 됩니다.
- 데이터가 쌓일수록 예상이 점점 나아질 수 있는 **기반**이 마련됩니다.
