# 계산 방식

> 앱의 계산을 **식과 상수 단위로** 적은 문서입니다. 1~10장은 홈 **확인할 사항**(대분류별 하루 비교), 11~17장은 나머지 계산(이어지는 변화, 총매출 분석, 홈 요약, 내일 예상 매출, 상권 판단, 식품 발주 점검, 요즘 뜨는 식품)입니다. 쉬운 설명은 [stats-guide.md](stats-guide.md)에 있습니다.
> 1~10장의 구현은 [backend/app/anomalies.py](../backend/app/anomalies.py)이고, 각 장의 숫자는 해당 파일 맨 위 상수와 같습니다. 숫자를 바꾸면 이 문서도 함께 고칩니다.
> 이 문서의 예시 숫자는 **설명용 가상 값**이며 실제 매출이 아닙니다.
> 관련 문서: [PRD.md](PRD.md)의 미정 7번(이상치 계산법) · [spec.md](spec.md) 3번과 "구현하면서 정한 세부 사항 (Phase 4)"

| 장 | 내용 | 구현 |
|---|---|---|

## 1. 한 줄 요약

**대분류마다 자기 자신의 "평소"(이전의 같은 요일·같은 시각까지의 기록)와 그날 판매액을 비교해서, 평소를 크게 벗어난 날을 "판매 변화가 큰 날"로 표시합니다.** 통계가 고르는 일이고, AI는 설명만 합니다. (AI 설명은 Phase 5)

## 2. 무엇을 비교하나

| 항목 | 내용 |
|---|---|
| **비교하는 숫자** | 대분류의 **하루 판매액**(원). 판매 수량이 아닙니다. (점주 확인) |
| **단위** | 대분류 하나하나를 따로 계산합니다. 다른 대분류의 값은 영향을 주지 않습니다. (점주 확인) |
| **파일에 줄이 없는 대분류** | 그날 **0원**으로 봅니다. (예: 담배 줄이 갑자기 없으면 "평소보다 적음"으로 올라옵니다) |
| **합계 줄** | 저장하지 않으므로 계산에 쓰이지 않습니다. |

### 비교 자료(= 평소)는 이렇게 고릅니다

분석하는 날짜를 **D**라고 하면, 평소는 다음 조건을 **모두** 만족하는 기록입니다.

1. **D보다 앞선 날짜**만 씁니다. D 이후의 자료는 절대 쓰지 않습니다.
2. D와 **같은 요일**입니다. (예: D가 월요일이면 이전의 월요일들)
3. D와 **같은 시각까지 집계**한 파일입니다. 마감 시각이 다르면 누적 금액이 달라서 비교가 틀어지므로 뺍니다.
4. 조건에 맞는 기록은 **쌓인 것 전부** 씁니다. 최근 몇 번으로 자르지 않습니다. (점주 확인: 쌓일수록 모두 반영)
5. **3번 이상** 쌓여야 판단합니다. 모자라면 정상·이상을 판정하지 않고 "데이터가 더 필요해요 (진행 n/3)"를 보여줍니다.

## 3. 이상한 날 판정 (보통 대분류)

평소 기록을 `h₁ … hₙ`, 그날 판매액을 `x`라고 합니다. (n ≥ 3)

```
중심      c = 중간값(h)
편차      MAD = 중간값( |hᵢ − c| )
흩어진 정도   scale = max( 1.4826 × MAD,  0.15 × c,  1,000원 )
점수      score = (x − c) ÷ scale
```

**이상한 날 = `|score| ≥ 3` 이고 `|x − c| ≥ 5,000원`** (둘 다 만족)

- `score > 0`이면 **평소보다 많음**, `score < 0`이면 **평소보다 적음**입니다.
- 화면의 "비교 기준 금액"은 `c`(중간값)이고, 금액 차이는 `x − c`, 증가율은 `(x − c) ÷ c`입니다. (`c`가 0이면 증가율은 계산하지 않고 금액 차이만 보여줍니다)

### 왜 평균이 아니라 중간값과 MAD인가

평균과 표준편차는 설 연휴처럼 **한 번 튄 값**에 크게 끌려갑니다. 기록이 몇 개 안 될 때는 그 영향이 더 큽니다. 중간값과 MAD(중간값 절대편차)는 튄 값에 덜 흔들립니다. `1.4826`은 MAD를 표준편차와 같은 눈금으로 맞추는 상수입니다. (정규분포일 때 MAD × 1.4826 ≈ 표준편차)

### 두 가지 안전장치

| 안전장치 | 이유 |
|---|---|
| `scale`에 **평소 중간값의 15%**, **1,000원** 하한 | 기록이 거의 똑같으면 MAD가 0에 가까워져 아주 작은 차이에도 점수가 폭발합니다. 하한이 이를 막습니다. |
| **차이 5,000원 이상** 조건 | 평소 1~2천 원짜리 대분류가 4천 원이 된 정도(비율은 크지만 의미 없는 변화)는 경고하지 않습니다. |

### 계산 예시 (가상)

| | |
|---|---|
| 같은 요일 평소 기록 6번 | 80,000 / 82,000 / 90,000 / 60,000 / 70,000 / 0원 (휴무일) |
| 중간값 `c` | 정렬하면 0, 60,000, 70,000, 80,000, 82,000, 90,000 → (70,000+80,000)÷2 = **75,000** |
| 각 값과 `c`의 차이 | 5,000 / 7,000 / 15,000 / 15,000 / 5,000 / 75,000 |
| `MAD` | 정렬하면 5,000, 5,000, 7,000, 15,000, 15,000, 75,000 → 중간값 = **11,000** |
| `scale` | max(1.4826 × 11,000 = 16,309, 0.15 × 75,000 = 11,250, 1,000) = **16,309** |
| 그날 판매액 `x` | 146,000원 |
| `score` | (146,000 − 75,000) ÷ 16,309 = **4.35** |
| 판정 | 4.35 ≥ 3 이고 차이 71,000 ≥ 5,000 → **평소보다 많음** |

## 4. 거의 늘 0원인 대분류 (예: 복권, 신변잡화)

평소 기록 중 **절반 이상(50% 이상)이 0원**이면 "거의 늘 0인 대분류"로 따로 봅니다. 대부분의 날이 0원이면 중간값이 0이 되어 위 공식이 의미를 잃기 때문입니다.

| 상황 | 처리 |
|---|---|
| 그날 판매액이 **0원** | 이상으로 보지 않습니다. 안 팔린 날은 평소 모습입니다. |
| 평소에 **팔린 날이 있었던** 경우 | **팔린 날의 금액끼리만** 위 공식(중간값·MAD·점수)으로 비교합니다. 비교 기준 금액은 "팔린 날의 중간값"입니다. |
| 평소에 **한 번도 안 팔렸던** 경우 | 그날 판매액이 **20,000원 이상**일 때만 "평소보다 많음"으로 올립니다. (비교 기준 0원) |

### 계산 예시 (가상)

- 평소 기록 7번: 0, 0, 0, 0, 4,000, 0, 0 → 0원이 6/7이므로 "거의 늘 0인 대분류".
- 팔린 날은 `[4,000]` 하나 → `c` = 4,000, `MAD` = 0 → `scale` = max(0, 0.15 × 4,000 = 600, 1,000) = **1,000**.
- 그날 13,000원 → `score` = (13,000 − 4,000) ÷ 1,000 = **9.0**, 차이 9,000 ≥ 5,000 → **평소보다 많음**.
- 그래프의 비교 기준선도 이 "팔린 날의 중간값"(4,000원)으로 그립니다. 판정에 쓴 기준과 화면의 기준이 같도록 하나의 함수(`baseline_of`)에서 계산합니다.

## 5. 홈 목록에 올리는 규칙

판정과 목록은 별개입니다. 판정은 모든 날짜에 대해 하고, 홈에는 이 규칙에 맞는 것만 올립니다.

1. **가장 최근에 올린 날짜로부터 7일 안**의 "판매 변화가 큰 날"만 올립니다. (점주 확인)
2. 점주가 **운영 상황을 기록한(= 처리한) 날은 빼고**, 아직 기록하지 않은 것만 올립니다. 기록 단위는 **대분류 + 날짜 하나**입니다.
3. 항목은 **(대분류, 날짜) 한 건씩** 보입니다. 같은 대분류가 여러 날이면 여러 줄입니다.
4. 가장 최근 올린 날짜의 변화는 **"오늘의 변화"**, 그 이전 날짜는 **"이전 미확인 사항"**으로 나눕니다. 한쪽만 있으면 그 이름이 카드 제목이 됩니다.
5. 오래된 변화(7일 밖)는 목록에서 빠지지만, 대분류 상세 그래프에는 계속 표시됩니다.
6. 최근 7일 안에 판단할 수 있는 날이 하나도 없으면(같은 요일 기록이 3번 미만) 정상·이상 판정 없이 **"판단 자료 부족"**을 보여줍니다.
7. 같은 날짜 파일을 **덮어쓰면** 그 날짜의 운영 상황 기록이 지워지고 새 숫자로 **다시 판정**합니다.

## 6. 매번 새로 계산됩니다

판정 결과는 저장하지 않고, 화면을 열 때마다 저장된 매출 기록 전부로 다시 계산합니다. 그래서:

- 파일을 새로 올리면 기록이 늘어 **평소 기준이 자동으로 갱신**됩니다. 이전 날짜의 판정도 새 기준으로 바뀔 수 있습니다.
- 올린 숫자를 덮어써도 따로 계산을 다시 돌릴 필요가 없습니다.
- 대분류 수와 기록이 많지 않아(대분류 약 20~30개 × 날짜 수백 개) 매번 계산해도 충분히 빠릅니다. 기록이 아주 많아지면 이 방식은 다시 검토합니다.

## 7. 이 방식의 성질과 한계

**가상 데이터 시뮬레이션** (대분류 15개, 평소 흔들림이 일정한 값):

| 평소 흔들림 | 기록 4번일 때 정상인데 뜨는 경고 | |
|---|---|---|
| 15% | 하루 약 0.1건 | 평소에 매우 안정적인 대분류 |
| 25% | 하루 약 0.9건 | 보통 |
| 35% | 하루 약 1.5건 | 흔들림이 큰 대분류 |

- 평소의 **2.5배**로 뛴 진짜 급증은 거의 100%(99.9%) 잡혔고, 1.6배는 약 65%였습니다.
- 기록이 쌓이면(6번 → 10번) 정상인데 뜨는 경고가 줄어듭니다. (25% 흔들림 기준 하루 0.56건 → 0.39건)

**알고 계실 한계**

- **연휴·행사·날씨:** 같은 요일끼리만 비교하므로 연휴나 장날(3·8일)의 영향은 반영하지 않습니다. 평소와 크게 달랐던 연휴 자체가 "변화가 큰 날"로 올라올 수 있고, 그 날이 이후 평소 기록에 섞이면 기준이 조금 흔들립니다.
- **하루 한 건 판정:** 대분류 수가 많으면 우연히 걸리는 경고가 있을 수 있습니다. "정상"이라고 기록하는 것은 이를 걸러내는 방법입니다.
- **기록이 적은 초반:** 3~5번일 때는 평소 중간값이 불안정합니다. 참고용으로 보시는 것이 안전합니다.
- **옛 자료의 영향:** 쌓인 기록을 전부 쓰므로 가게 상황이 크게 바뀌면(상권·메뉴 변화) 옛 기록이 평소를 왜곡할 수 있습니다. 반년쯤 쌓이면 최근 기간만 쓸지 검토합니다.
- **임계값은 가상 데이터 기준:** `점수 3`, `5,000원` 같은 값은 가상 데이터로 정한 초기값입니다. 실제 파일이 쌓이면 다시 조정합니다. (PRD 미정 7번의 남은 부분)

## 7-1. 이어지는 변화와 0원이 많은 분류 (추가 방식)

위의 하루 비교는 **하루짜리 큰 변화**에 강하지만 급감·품절, 며칠 이어지는 변화, 0원이 많은 분류의 안 팔림은 거의 놓칩니다. 그래서 기록이 **28일 이상** 쌓이면 [backend/app/detection.py](../backend/app/detection.py) 가 함께 판단합니다. 같은 칸을 두 방법이 모두 알리면 위의 하루 비교를 남깁니다. 쉬운 설명과 따라 해 볼 수 있는 예시는 [stats-guide.md](stats-guide.md) 1장, 시연 데이터 평가는 [lab.md](lab.md)에 있습니다.

| 분류 종류 (팔린 날 비율) | 방법 |
|---|---|
| 거의 매일 팔림 (90% 이상) | 요일 효과를 뺀 점수로 **Shewhart**(하루 점수 ≥ c, 5,000원 이상) + **CUSUM**(누적 > h) |
| 0원이 많음 (15~90%) | ① 팔린 날 비율 CUSUM(h) ② 팔린 날 금액 (위와 같은 방법, 기록 15일부터) |
| 거의 안 팔림 (15% 미만) | 평소보다 많이 팔린 날만: 수량이 지금까지 최대보다 많고 평소의 2배 이상, 금액이 수량 많았던 날만큼, 차이가 최소 금액 이상 |
| 한 번도 안 팔림 | 판단하지 않음 |

- 값은 로그(금액 + 1,000)로 바꿔 봅니다. 요일 효과는 **앞선 기록**으로 구해 먼저 빼고(같은 요일 기록이 적으면 0쪽으로 당김), 평소 수준은 최근 84일의 중간값입니다.
- CUSUM: 점수를 ±4로 자른 뒤 허용치 0.5를 빼며 위·아래를 따로 누적하고, 기준을 넘으면 알리고 0으로 되돌립니다.
- 같은 시각까지의 매출끼리만 비교합니다. 업로드가 없는 날은 건너뛰므로 "며칠째"는 올린 날 기준입니다.
- **휴일은 아직 반영하지 않습니다.** (시연 데이터 평가 도구는 알려진 휴일을 건너뛰지만 앱에는 휴일표가 없습니다. 연휴가 알림으로 올라올 수 있습니다)
- 알림 종류: `daily`(하루 점수) · `trend`(이어지는 변화) · `streak`(팔린 날 비율이 바뀜) · `big_sale`(거의 안 팔리는 분류가 많이 팔림). 화면에는 `daily`가 아닌 것만 한 줄 설명을 붙입니다.

### 민감도 (설정 화면)

| 민감도 | 하루 비교 점수 | 매일 팔림 (Shewhart, CUSUM) | 팔린 날 비율 CUSUM | 0원 많음 금액 (Shewhart, CUSUM) | 거의 안 팔림 최소 금액 |
|---|---|---|---|---|---|
| 낮음 | 4.0 | 4.0 / 8.0 | 5.0 | 4.0 / 8.0 | 5,000원 |
| **보통 (기본)** | 3.0 | 4.0 / 5.0 | 4.0 | 4.0 / 5.0 | 3,000원 |
| 높음 | 2.5 | 3.0 / 4.0 | 3.0 | 3.0 / 4.0 | 2,000원 |

값은 `detection.py`의 `LEVELS`에 있고, 선택은 DB의 `app_settings` 테이블에 저장됩니다(없으면 보통).

## 11. 이어지는 변화·0원이 많은 분류의 계산 (detection.py)

7-1의 요약을 단계별 식으로 풀어 쓴 절입니다. 구현은 [backend/app/detection.py](../backend/app/detection.py)이고 숫자는 그 파일 맨 위 상수와 같습니다. 쉬운 설명은 [stats-guide.md](stats-guide.md) 1장입니다.

### 11-1. 입력과 분류 종류
- **입력:** 같은 시각까지 집계한 업로드의 날짜(오래된 순)와, 분류별 날짜별 판매액·수량. 업로드가 없는 날은 건너뛰므로 "며칠째"는 올린 날 기준입니다.
- **판단 시작:** 날짜가 **28개를 넘어야**(`n > MIN_HISTORY`) 시작하고, 각 날을 판단할 때는 **그날 이전 기록만** 씁니다. 기록이 28개 미만이면 새 방식은 아무것도 알리지 않습니다.
- **분류 종류:** 전체 날짜 중 판매액이 0보다 큰 날의 비율 `f`로 정합니다.

| f | 종류 | 방법 |
|---|---|---|
| ≥ 0.90 | dense | 11-2 ~ 11-4 |
| 0.15 ≤ f < 0.90 | mid | 11-5 |
| 0 < f < 0.15 | rare | 11-6 |
| 0 | none | 판단하지 않음 |

### 11-2. 점수 z 만들기 (`score_series`)
날마다 아래 순서로 구합니다. `recent`는 그날 이전의 최근 **84일**(`WINDOW`)이고 28개 이상이어야 합니다.

```
ℓ(금액)     = ln(금액 + 1,000)
overall     = 중간값( ℓ  for recent )                         # 평소 수준
요일 g의 효과 = 중간값( ℓⱼ − overall  for 요일이 g인 j ) × m ÷ (m + 4)   # m = 그 요일 기록 수, 4 = SHRINK
잔차 rⱼ     = ℓⱼ − overall − 효과(요일(j))
center      = 중간값(r),  MAD = 중간값( |r − center| )
scale       = max( 1.4826 × MAD,  0.15 )                       # 0.15 = SCALE_FLOOR, 로그 단위
기대 로그    = overall + 효과(그날의 요일)                      # 그 요일을 본 적이 없으면 효과 0
z           = ( ℓ(오늘) − 기대 로그 ) ÷ scale
기대 금액    = e^(기대 로그) − 1,000
```

- **0쪽으로 당기는 비율** `m ÷ (m + 4)`: 같은 요일 기록 m이 4면 0.50, 8이면 0.67, 12면 0.75입니다. 창이 84일이라 한 요일은 **최대 12개**이므로 효과는 **최대 75%**만 반영됩니다.
- 업로드 날짜가 `skip`에 해당하면(앱에서는 쓰지 않음) 기록에도 알림에도 넣지 않습니다.

> **계산 예 (가상):** 기대 금액이 9만 원이고 scale이 0.25인 분류에서 오늘 2.5만 원이면
> ℓ(오늘) − 기대 로그 = ln(26,000 ÷ 91,000) = −1.253 → z = −1.253 ÷ 0.25 = **−5.0**.
> (1,000을 더하므로 stats-guide의 간단한 예시 −5.1과 약간 다릅니다.)

### 11-3. 알림 두 가지 (`alarms_of`)
```
Shewhart : |z| ≥ c   그리고   |오늘 금액 − 기대 금액| ≥ 5,000원      → 알림 종류 daily
CUSUM    : zc = z를 −4 ~ +4로 자른 값
           up   = max(0, up   + zc − 0.5)     # K = 0.5
           down = max(0, down − zc − 0.5)
           up 또는 down이 h를 넘으면 알림(trend)하고 그쪽 누적만 0으로 되돌림
```
- 판단을 건너뛴 날(기록 부족)은 누적도 하지 않습니다.
- `c`, `h`는 민감도에서 옵니다(7-1의 표). 보통 단계의 dense는 c = 4.0, h = 5.0입니다.

### 11-4. 같은 칸에 알림이 겹칠 때
한 칸(분류 × 날짜)에 알림이 여러 개면 **하루 점수(daily) > 많이 팔림(big_sale) > 며칠째 변화(streak) > 이어지는 변화(trend)** 순으로 하나만 남깁니다. 기존 방식(3장)과도 겹치면 기존 방식의 설명을 보여 줍니다.

### 11-5. 0원이 많은 분류 (mid)
**① 팔린 날 비율 CUSUM (`occurrence_alarms`)**
```
p0     = 가장 가까운 84일의 (팔린 날 수 + 0.5) ÷ (기록 수 + 1)을 0.05 ~ 0.95로 자른 값
p_down = p0 ÷ 2                       # "절반으로 줄었다"는 가정
p_up   = p0 + (1 − p0) ÷ 2            # "남은 몫의 절반만큼 늘었다"는 가정
매일 더하는 점수
  팔린 날   : down += ln(p_down ÷ p0)              up += ln(p_up ÷ p0)
  안 팔린 날 : down += ln((1−p_down) ÷ (1−p0))     up += ln((1−p_up) ÷ (1−p0))
down, up은 0 밑으로 내려가지 않고, h(민감도의 occ)를 넘으면 알림(streak)하고 0으로 되돌림
```
**점수는 평소 비율 p0에 따라 달라집니다.** 팔린 날은 항상 ln 0.5 = −0.693이지만, 안 팔린 날의 점수는 아래처럼 p0이 높을수록 큽니다. (보통 단계 h = 4일 때, 줄어드는 쪽 알림이 나기까지 연속으로 안 팔려야 하는 날수)

| p0 | p_down | 안 팔린 날 점수 | 연속 안 팔림 날수(h=4) |
|---|---|---|---|
| 0.8 | 0.4 | ln 3 = +1.099 | 4일 (4×1.099 = 4.39) |
| 0.6 | 0.3 | ln(0.7÷0.4) = +0.560 | 8일 (7일은 3.92로 못 넘음) |
| 0.5 | 0.25 | ln(0.75÷0.5) = +0.405 | 10일 (9일은 3.65) |

표의 날수는 p0을 고정했을 때의 값입니다. 실제로는 안 팔린 날이 84일 창에 들어오면서 p0이 조금씩 내려가 점수가 작아지므로 한두 날 더 걸릴 수 있습니다. (시험 삼아 돌려 보면 p0 0.8은 4일, 0.6은 8일, 0.5는 11일째에 알림이 났습니다.)

그래서 "4일째 알림"은 평소 비율이 0.8일 때의 예이고, 평소 비율이 낮은 분류일수록 더 오래 안 팔려야 알립니다. 요일 효과는 빼지 않습니다.

**② 팔린 날의 금액:** 판매액이 0보다 큰 날만 모아 11-2, 11-3을 그대로 적용합니다. 다만 평소를 정하는 창은 **60일**(`SPARSE_WINDOW`), 판단에 필요한 팔린 날 기록은 **15개**(`SPARSE_MIN_HISTORY`)이고, 기준은 민감도의 `mid_amount`입니다.

### 11-6. 거의 안 팔리는 분류 (rare, `is_big_sale`)
팔린 날(판매액 > 0)마다 **그날 이전**의 팔린 날 기록 `own`(이 분류)과 `pooled`(거의 안 팔리는 모든 분류를 합친 것)로 판단합니다. `q`는 수량, `a`는 금액입니다.

```
① 수량 조건
   own이 5개 이상 : q > max(own 수량)  그리고  q ≥ 2 × 중간값(own 수량)
   아니고 pooled가 5개 이상 : q ≥ max( 5,  pooled 수량의 90번째 백분위수 )
   둘 다 아니면 : q ≥ 5
② 금액 조건 (기준 기록 = ①에서 쓴 own 또는 pooled, 기준이 없으면 건너뜀)
   a ≥ 중간값( 기준 기록 중 수량이 75번째 백분위수 이상인 날의 금액 )
③ 최소 금액 차이
   a − 중간값(own 금액, own이 없으면 0) ≥ 최소 금액   # 민감도의 rare_gap: 5,000 / 3,000 / 2,000원
셋 다 만족하면 알림(big_sale)
```
- 백분위수는 값을 줄 세워 `번호 = int(q × (개수 − 1) + 0.5)`번째를 고르는 단순한 방식입니다.
- 안 팔린 날(0원)은 판단하지 않고, 평소 판매는 알리지 않습니다.

## 12. 총매출 분석의 "평소 범위" (sales_detail.py)

**자료:** 오늘보다 앞선 **모든 요일**의 총매출 중 **같은 시각까지 집계한 것 전부** `history`. 3개 미만이면 판단하지 않습니다(`not_enough`).

```
값        = ln(금액)   (history와 오늘이 모두 0보다 클 때, 아니면 금액 그대로)
μ         = 평균(값),  s = 표본표준편차(값)      # s가 0이면 판단하지 않음(no_variation)
n         = history 개수,  자유도 df = n − 1
spread    = s × √(1 + 1/n)                        # 새 값 하나가 흩어지는 정도
t         = ( 오늘 값 − μ ) ÷ spread
p         = 2 × ( 1 − t분포 누적(|t|, df) )
crit      = t분포의 97.5% 지점(df)                 # ALPHA = 0.05, 양쪽
평소 중심   = e^μ,   범위 = e^(μ ± crit × spread)   # 로그를 쓰지 않았으면 e^ 없이, 아래쪽은 0원 아래로 내리지 않음
판정       = p ≥ 0.05 → 범위 안, 아니면 t > 0 → 평소보다 높음, t < 0 → 평소보다 낮음
```
- `√(1 + 1/n)`의 `1/n`은 "평균 자체도 불확실하다"는 몫이고, n이 작을수록 `crit`(t 분포)도 커져서 범위가 넓어집니다.
- 기록이 5개 미만이면 "자료가 적어 참고용" 표시를 붙입니다(`FEW_DATA_UNDER`).
- 분포 안의 위치는 `min(t분포 누적(t), 1 − 누적) × 100`%로 "상위/하위 x%"를 보여 줍니다. 오늘보다 낮았던 기록 수도 함께 셉니다.
- t 분포 계산은 `stats.py`가 외부 라이브러리 없이 직접 합니다.

> **계산 예 (가상):** history = 8만, 9만, 8.5만, 9.5만, 8.8만, 7만 (n = 6)
> μ = 11.342(→ 평소 중심 **84,271원**), s = 0.1075, spread = 0.1161, df = 5, crit = 2.571 → 범위 **62,526 ~ 113,576원**.
>
> | 오늘 | t | p | 판정 |
> |---|---|---|---|
> | 6만 원 | −2.93 | 0.033 | **평소보다 낮음** (범위 아래) |
> | 9.5만 원 | +1.03 | 0.349 | 범위 안 |
> | 15만 원 | +4.97 | 0.004 | **평소보다 높음** |

## 13. 홈 "매출 요약"의 비교 (home.py)

- **비교 자료:** 마지막으로 올린 날(오늘)보다 앞선 업로드 중 **같은 요일**, **같은 시각까지 집계**한 것 가운데 **최근 4번**(`MAX_SAME_WEEKDAY_DAYS`). 3번 미만이면 "데이터가 더 필요해요(진행 n/3)"를 보여 줍니다.
- **계산:** 각 날의 총 판매액·총 수량을 구해서 4번의 **단순 평균**을 평소로 삼습니다.
```
증감률(%) = ( 오늘 − 평소 ) ÷ 평소 × 100     # 소수 첫째 자리까지, 평소가 0이면 계산하지 않음
```
- 정상·이상 판정은 하지 않고 증감률만 보여 줍니다. 마감 시각이 다른 날은 비교에서 빼고 몇 건을 뺐는지 알립니다.

> **계산 예 (가상):** 같은 요일 4번의 총 판매액이 90만, 100만, 110만, 100만이면 평소 100만 원. 오늘 118만 원이면 (118 − 100) ÷ 100 × 100 = **+18.0%**.

## 14. 내일 예상 매출 (forecast.py)

쉬운 설명과 다른 모형과의 비교 표는 [stats-guide.md](stats-guide.md) 3장입니다. 여기서는 계산 순서와 상수만 적습니다.

### 14-1. 자료
- 총매출은 마지막 업로드와 **같은 시각까지 집계한 날만**, 0보다 큰 것만 씁니다. 날이 **12일 미만**이면 예상하지 않습니다(`MIN_DAYS`).
- 달력(장날·공휴일·방학)은 설정에 저장된 것, 날씨는 기상청 ASOS 관측값(가장 가까운 관측소가 50km 이내일 때만)을 씁니다. 비 온 날은 하루 강수량 **1mm 이상**입니다.
- **예상 대상 날짜**는 마지막 업로드 다음 날이고, 그날 날씨는 저장된 관측값이 있으면 그것을, 없고 오늘 이후면 단기예보를 씁니다. 둘 다 없으면 날씨 없이 계산합니다.

### 14-2. 회귀식
```
ln(총매출) = 상수 + (화~일 요일 6개: 월요일이 기준) + 장날 + 공휴일 + 방학 + 기온 + 비 온 날 + 남는 차이
```
- 설명 변수는 날씨가 있으면 11개(요일 6 + 달력 3 + 날씨 2), 없으면 9개입니다. 장날·공휴일·방학·비 온 날은 0/1, 기온은 그날 평균 기온(도)입니다.
- 각 변수(상수 제외)는 학습 기간의 평균을 빼고 표준편차로 나눠 **같은 눈금**으로 맞춘 뒤 푸는데, 결과는 다시 원래 눈금의 계수로 되돌립니다.
- **릿지:** 상수를 뺀 계수에 `λ × (계수)²`의 벌금을 매겨 풉니다(닫힌 식, 역행렬을 직접 계산).
- **λ 고르기:** 후보 `{0.5, 2, 5, 10, 20, 50, 100}` 중, 하루씩 빼고 맞혀 본 오차의 절대값 합이 가장 작은 값. 빼고 맞힌 오차는 다시 학습하지 않고 `(실제 − 예상) ÷ (1 − 대각 영향값)` 식으로 한 번에 구합니다.
- **최근 오차 보정:** 학습한 식이 **최근 14일**에서 평균적으로 빗나간 로그 오차의 **절반**(`LEVEL_SHARE`)을 예상에 더합니다. 예상 = `exp( Σ 계수 × 값 + 보정 )`.

### 14-3. 걸러서 맞혀 보기와 방법 고르기
```
맞혀 볼 날    = 마지막 45일 (첫 학습 최소 28일, 자료가 40일 미만이면 8일)
각 날마다     = 그날 이전 자료만으로 회귀식을 만들어 예상 (λ는 10일마다 다시 고름)
평소 기준 1   = 같은 요일 최근 8번의 중간값 (같은 요일이 3번 미만이면 최근 56일 중간값)
평소 기준 2   = 최근 56일의 중간값
평균 오차     = 평균( |예상 − 실제| ÷ 실제 ) × 100
보통의 날 오차 = 중간값( |예상 − 실제| ÷ 실제 ) × 100
```
**모형을 쓰는 조건 (모두 만족):** 맞혀 본 날 ≥ 15, 모형 평균 오차 ≤ 0.95 × (두 평소 기준 중 평균 오차가 더 작은 쪽), 모형의 보통의 날 오차 ≤ 그 기준의 보통의 날 오차. 하나라도 못 맞추면 평소 기준(평균 오차가 더 작은 쪽)을 중심값으로 씁니다.

> **계산 예 (가상):** 45일 중 맞혀 본 날 45, 모형 평균 오차 24%, 평소 기준 중 나은 쪽 30%라면 0.95 × 30 = 28.5 ≥ 24이고 보통의 날 오차도 모형이 낮으면 **모형을 씁니다.** 모형이 29%였다면 28.5를 넘어 평소 기준을 씁니다.

### 14-4. 범위
```
로그 오차  = ln( 실제 ÷ 예상 )   (쓰기로 한 방법의 맞혀 본 날 전부, 8일 이상이어야 범위를 말함)
아래 끝    = 중심 × e^( min(10% 지점, 0) × 넓힘 )
위 끝      = 중심 × e^( max(90% 지점, 0) × 넓힘 )       # 지점은 줄 세워 선형으로 보간
넓힘       = 모형이고 날씨를 예보로 썼을 때 1.1, 그 밖에는 1.0
```
- 모형일 때 화면에는 오늘 조건에 해당하는 요인(장날·공휴일·방학·비 온 날의 `(e^계수 − 1) × 100`%, 기온은 학습 기간 평균과의 차이에 대한 효과)을 함께 보여 줍니다. 예: 계수가 −0.0834면 `e^−0.0834 − 1 = −8.0%`.
- 날씨 변수는 날씨가 있는 날이 8일 이상일 때만 씁니다. 실제 23일 자료에서는 모형이 평소 기준을 이기지 못해 평소 기준을 쓰므로, 날씨를 바꿔도 예상이 변하지 않는 것이 정상 동작입니다.

## 15. 주변 상권 판단 (suggestions.py의 상권 사실)

모두 **숫자 하나를 기준선과 비교하는 규칙**이고, 기준선은 통계로 구한 값이 아니라 **사람이 정한 가정값**입니다. 해석은 "일반적인 추정"으로만 표시하고, AI는 이 결과를 문장으로 풀어 쓰기만 합니다.

| 판단 | 식 | 기준 (상수) |
|---|---|---|
| 학생 상권 | 반경 500m 안 학교 수, 점포 앞 100m 안 학원 수 | 학교 ≥ 1 **또는** 학원 ≥ 3 (`ACADEMY_MIN`) |
| 직장인 상권 | `비율 = 종사자 ÷ 거주 인구` (같은 동) | ≥ 1.0 (`OFFICE_RATIO`) 직장인 상권, 0.5 ≤ 비율 < 1.0 (`OFFICE_SOME_RATIO`) 직장인도 있는 동네 |
| 주거 상권 | 위와 같은 비율 | < 0.5 (`HOME_RATIO`). 가구당 평균 인원 ≤ 2.2 (`SMALL_FAMILY`)면 "1~2인 가구가 많은 편"을 덧붙임 |
| 교통 상권 | 반경 500m 안 지하철역 수 | ≥ 1 (`STATION_MIN`) |
| 동네 연령 구성 | `연령대 인구 ÷ 연령대 인구의 합` | 판단이 아니라 비율 계산(총인구가 아닌 연령대 합이 분모) |

- 대학 방학은 "6월 21일~8월 31일, 12월 21일~2월 28일"이라는 **일반적인 달력 어림**이고 항상 "학교마다 다르다"를 붙입니다.
- 반경 500m는 걸어서 5~7분이라는 어림입니다. 종사자·인구는 통계청 동 단위 숫자라 반경과 범위가 다릅니다.

> **계산 예 (가상):** 종사자 8,000명, 거주 인구 20,000명 → 비율 0.4 < 0.5 → 주거 중심. 가구당 1.8명이면 "1~2인 가구가 많은 편"까지 덧붙입니다. 같은 동에서 종사자가 22,000명이면 비율 1.1 ≥ 1.0 → 직장인 상권.

## 16. 식품 발주 점검 신호 (stock.py)

쉬운 설명은 [stats-guide.md](stats-guide.md) 6장입니다. 입출고 자료는 **가상의 형식**을 가정하고 만들었고 기준값은 모두 **검증 전 초기값**입니다.

### 16-1. 하루 수치와 걸러 내기
```
팔 수 있던 수량  = 기초재고 + 입고수량
소진율          = 판매수량 ÷ 팔 수 있던 수량        (팔 수 있던 수량이 0이면 계산하지 않음)
폐기율          = 폐기수량 ÷ 팔 수 있던 수량
재고가 맞는 줄   = 기초재고 + 입고 = 판매 + 폐기 + 반품 + 기말재고
다 팔림(추정)    = 기말재고 0 이고 폐기 0 이고 팔 수 있던 수량 > 0
일찍 품절        = 품절시각 ≤ 22 − 3 = 19시   (품절시각이 있는 기록에서만)
```
- **판단에 쓰는 기록:** 재고가 맞고, 팔 수 있던 수량이 **5개 이상**인 줄만.
- **행사 날은 따로** 모읍니다. 평소 판단은 **행사가 아닌 최근 5번**(`window`)만 쓰고, 행사 줄은 최근 5번을 따로 보여 줍니다.
- **기간 합산:** 화면의 소진율·폐기율은 `Σ 판매 ÷ Σ 팔 수 있던 수량`으로, 하루 소진율의 평균과 다를 수 있습니다. 이월 재고(기초재고 > 0)가 있으면 같은 상품이 여러 날의 분모에 들어갑니다.

### 16-2. 신호를 정하는 순서
위에서부터 처음 맞는 것 하나만 냅니다. `high` = 소진율 ≥ 0.90인 날, `waste` = 폐기율 ≥ 0.20인 날, `stockout` = 일찍 품절한 날(품절시각이 한 번이라도 있는 상품) 또는 다 팔림(추정, 품절시각이 하나도 없는 상품).

| 순서 | 신호 | 조건 (모두 만족) |
|---|---|---|
| 1 | 판단하지 않음(insufficient) | 행사 없는 기록이 5번 미만, 또는 그 5번의 팔 수 있던 수량 합이 30개 미만 |
| 2 | 증량 검토(increase_review) | `high` ≥ 4일, `stockout` ≥ 3일, 합산 폐기율 ≤ 0.05 |
| 3 | 참고(balanced) | `high` ≥ 4일 (2번이 아닐 때: 일찍 품절 없음) |
| 4 | 폐기 점검(decrease_review) | `waste` ≥ 3일, 합산 소진율 ≤ 0.70 |
| 5 | 행사 비교(promo_only) | 행사 날 최근 3번 중 2번 이상이 있고 모두 소진율 ≥ 0.90, 그리고 행사 없는 `high` ≤ 1일 |
| 6 | 특별한 신호 없음(none) | 위에 모두 해당 없음 |

> **계산 예 (가상):** 행사 없는 최근 5번, 날마다 팔 수 있던 수량 10개.
>
> | 날 | 판매 | 폐기 | 기말재고 | 소진율 | 품절시각 |
> |---|---|---|---|---|---|
> | 1 | 10 | 0 | 0 | 100% | 15시 |
> | 2 | 10 | 0 | 0 | 100% | 16시 |
> | 3 | 9 | 1 | 0 | 90% | 없음 |
> | 4 | 10 | 0 | 0 | 100% | 14시 |
> | 5 | 10 | 0 | 0 | 100% | 17시 |
>
> 합산: 팔 수 있던 수량 50(≥ 30), 판매 49 → 소진율 98%, 폐기 1 → 폐기율 2%(≤ 5%). `high` 5일(≥ 4), 품절시각이 있으니 19시 이전 품절 4일(≥ 3) → **증량 검토.** 날 3처럼 품절시각이 비어 있으면 일찍 품절로 세지 않습니다.

## 17. 요즘 뜨는 식품 집계 (trend_today.py, trend_discover.py)

통계 모형이 아니라 **세기**입니다. 쉬운 설명은 [stats-guide.md](stats-guide.md) 8장, 정의와 한계는 [trends.md](trends.md)입니다.

```
받는 양      = 해시태그 7개 × 30건 = 최대 210건 (하루 1회. 이번 달 사용량 + 210이 1,500건을 넘으면 돈을 쓰기 전에 막음)
어림 비용     = 해시태그 수 × 건수 ÷ 1,000 × 2.6달러 = 약 0.55달러 (비용 상한 0.65달러보다 크면 돈을 쓰기 전에 막음)
안전 글       = 글에서 공백을 빼고 소문자로 바꾼 뒤 SAFETY_WORDS(회수·판매중단·판매중지·부적합·검출·리콜·이물질·식중독·대장균·섭취중단·섭취금지)가 하나라도 있는 글
이름 찾기     = AI가 전체 글(300건까지)에서 상품 이름 후보(최대 12개, 이름 길이 2~20자)와 별칭을 고름
건수          = 안전 글이 아닌 글 중, 공백을 빼고 소문자로 바꾼 글에 이름 또는 별칭이 들어 있는 글의 수 (코드가 전체 글에서 다시 셈, AI가 말한 건수는 쓰지 않음)
계정 수       = 그 글들을 쓴 서로 다른 계정 수
보여 주는 조건 = 건수 ≥ 2 그리고 계정 수 ≥ 2
순서          = 건수 많은 순, 같으면 계정 수 많은 순, 그래도 같으면 이름순
```
- 같은 글(같은 게시물 코드)은 한 번만 셉니다. 안전 글에 같은 상품 이름이 있으면 `safety_posts`로 따로 세어 카드에 "안전 관련 언급 있음"을 표시합니다.
- 상품마다 근거 글은 최대 5건, 주의 영역의 안전 글은 최대 5건 보여 줍니다.
- 이 숫자는 **받은 표본 안에서의 건수**일 뿐이고, 검색량이나 증가를 뜻하지 않습니다.

> **계산 예 (가상):** 받은 글 210건에서 중복을 빼 200건, 안전 글 10건을 빼면 190건. "피자설기"가 별칭 포함 14건·계정 11곳에 들어 있으면 14건으로 순위에 오르고, 이름이 한 글에만 나온 상품은 건수 1이라 숨깁니다.
