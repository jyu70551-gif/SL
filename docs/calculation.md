# 계산 방식: 대분류별 판매 변화 ("확인할 사항")

> 홈의 **확인할 사항**이 어떤 대분류를, 어떤 계산으로 골라내는지 적은 문서입니다.
> 구현은 [backend/app/anomalies.py](../backend/app/anomalies.py)이고, 이 문서의 숫자는 그 파일 맨 위 상수와 같습니다. 숫자를 바꾸면 이 문서도 함께 고칩니다.
> 이 문서의 예시 숫자는 **설명용 가상 값**이며 실제 매출이 아닙니다.
> 관련 문서: [PRD.md](PRD.md)의 미정 7번(이상치 계산법) · [spec.md](spec.md) 3번과 "구현하면서 정한 세부 사항 (Phase 4)"

---

## 1. 한 줄 요약

**대분류마다 자기 자신의 "평소"(이전의 같은 요일·같은 시각까지의 기록)와 그날 판매액을 비교해서, 평소를 크게 벗어난 날을 "판매 변화가 큰 날"로 표시합니다.** 통계가 고르는 일이고, AI는 설명만 합니다. (AI 설명은 Phase 5)

---

## 2. 무엇을 비교하나

| 항목 | 내용 |
|---|---|
| **비교하는 숫자** | 대분류의 **하루 판매액**(원). 판매 수량이 아닙니다. (점주 확인) |
| **단위** | 대분류 하나하나를 따로 계산합니다. 다른 대분류의 값은 영향을 주지 않습니다. (점주 확인) |
| **파일에 줄이 없는 대분류** | 그날 **0원**으로 봅니다. (예: 담배 줄이 갑자기 없으면 "평소보다 적음"으로 올라옵니다) |
| **합계 줄** | 저장하지 않으므로 계산에 쓰이지 않습니다. |

### 비교 자료(= 평소)는 이렇게 고릅니다

분석하는 날짜를 **D**라고 하면, 평소는 다음 조건을 **모두** 만족하는 기록입니다.

1. **D보다 앞선 날짜**만 씁니다. D 이후의 자료는 절대 쓰지 않습니다.
2. D와 **같은 요일**입니다. (예: D가 월요일이면 이전의 월요일들)
3. D와 **같은 시각까지 집계**한 파일입니다. 마감 시각이 다르면 누적 금액이 달라서 비교가 틀어지므로 뺍니다.
4. 조건에 맞는 기록은 **쌓인 것 전부** 씁니다. 최근 몇 번으로 자르지 않습니다. (점주 확인: 쌓일수록 모두 반영)
5. **3번 이상** 쌓여야 판단합니다. 모자라면 정상·이상을 판정하지 않고 "데이터가 더 필요해요 (진행 n/3)"를 보여줍니다.

## 3. 이상한 날 판정 (보통 대분류)

평소 기록을 `h₁ … hₙ`, 그날 판매액을 `x`라고 합니다. (n ≥ 3)

```
중심      c = 중간값(h)
편차      MAD = 중간값( |hᵢ − c| )
흩어진 정도   scale = max( 1.4826 × MAD,  0.15 × c,  1,000원 )
점수      score = (x − c) ÷ scale
```

**이상한 날 = `|score| ≥ 3` 이고 `|x − c| ≥ 5,000원`** (둘 다 만족)

- `score > 0`이면 **평소보다 많음**, `score < 0`이면 **평소보다 적음**입니다.
- 화면의 "비교 기준 금액"은 `c`(중간값)이고, 금액 차이는 `x − c`, 증가율은 `(x − c) ÷ c`입니다. (`c`가 0이면 증가율은 계산하지 않고 금액 차이만 보여줍니다)

### 왜 평균이 아니라 중간값과 MAD인가

평균과 표준편차는 설 연휴처럼 **한 번 튄 값**에 크게 끌려갑니다. 기록이 몇 개 안 될 때는 그 영향이 더 큽니다. 중간값과 MAD(중간값 절대편차)는 튄 값에 덜 흔들립니다. `1.4826`은 MAD를 표준편차와 같은 눈금으로 맞추는 상수입니다. (정규분포일 때 MAD × 1.4826 ≈ 표준편차)

### 두 가지 안전장치

| 안전장치 | 이유 |
|---|---|
| `scale`에 **평소 중간값의 15%**, **1,000원** 하한 | 기록이 거의 똑같으면 MAD가 0에 가까워져 아주 작은 차이에도 점수가 폭발합니다. 하한이 이를 막습니다. |
| **차이 5,000원 이상** 조건 | 평소 1~2천 원짜리 대분류가 4천 원이 된 정도(비율은 크지만 의미 없는 변화)는 경고하지 않습니다. |

### 계산 예시 (가상)

| | |
|---|---|
| 같은 요일 평소 기록 6번 | 80,000 / 82,000 / 90,000 / 60,000 / 70,000 / 0원 (휴무일) |
| 중간값 `c` | 정렬하면 0, 60,000, 70,000, 80,000, 82,000, 90,000 → (70,000+80,000)÷2 = **75,000** |
| 각 값과 `c`의 차이 | 5,000 / 7,000 / 15,000 / 15,000 / 5,000 / 75,000 |
| `MAD` | 정렬하면 5,000, 5,000, 7,000, 15,000, 15,000, 75,000 → 중간값 = **11,000** |
| `scale` | max(1.4826 × 11,000 = 16,309, 0.15 × 75,000 = 11,250, 1,000) = **16,309** |
| 그날 판매액 `x` | 146,000원 |
| `score` | (146,000 − 75,000) ÷ 16,309 = **4.35** |
| 판정 | 4.35 ≥ 3 이고 차이 71,000 ≥ 5,000 → **평소보다 많음** |

## 4. 거의 늘 0원인 대분류 (예: 복권, 신변잡화)

평소 기록 중 **절반 이상(50% 이상)이 0원**이면 "거의 늘 0인 대분류"로 따로 봅니다. 대부분의 날이 0원이면 중간값이 0이 되어 위 공식이 의미를 잃기 때문입니다.

| 상황 | 처리 |
|---|---|
| 그날 판매액이 **0원** | 이상으로 보지 않습니다. 안 팔린 날은 평소 모습입니다. |
| 평소에 **팔린 날이 있었던** 경우 | **팔린 날의 금액끼리만** 위 공식(중간값·MAD·점수)으로 비교합니다. 비교 기준 금액은 "팔린 날의 중간값"입니다. |
| 평소에 **한 번도 안 팔렸던** 경우 | 그날 판매액이 **20,000원 이상**일 때만 "평소보다 많음"으로 올립니다. (비교 기준 0원) |

### 계산 예시 (가상)

- 평소 기록 7번: 0, 0, 0, 0, 4,000, 0, 0 → 0원이 6/7이므로 "거의 늘 0인 대분류".
- 팔린 날은 `[4,000]` 하나 → `c` = 4,000, `MAD` = 0 → `scale` = max(0, 0.15 × 4,000 = 600, 1,000) = **1,000**.
- 그날 13,000원 → `score` = (13,000 − 4,000) ÷ 1,000 = **9.0**, 차이 9,000 ≥ 5,000 → **평소보다 많음**.
- 그래프의 비교 기준선도 이 "팔린 날의 중간값"(4,000원)으로 그립니다. 판정에 쓴 기준과 화면의 기준이 같도록 하나의 함수(`baseline_of`)에서 계산합니다.

## 5. 홈 목록에 올리는 규칙

판정과 목록은 별개입니다. 판정은 모든 날짜에 대해 하고, 홈에는 이 규칙에 맞는 것만 올립니다.

1. **가장 최근에 올린 날짜로부터 7일 안**의 "판매 변화가 큰 날"만 올립니다. (점주 확인)
2. 점주가 **운영 상황을 기록한(= 처리한) 날은 빼고**, 아직 기록하지 않은 것만 올립니다. 기록 단위는 **대분류 + 날짜 하나**입니다.
3. 항목은 **(대분류, 날짜) 한 건씩** 보입니다. 같은 대분류가 여러 날이면 여러 줄입니다.
4. 가장 최근 올린 날짜의 변화는 **"오늘의 변화"**, 그 이전 날짜는 **"이전 미확인 사항"**으로 나눕니다. 한쪽만 있으면 그 이름이 카드 제목이 됩니다.
5. 오래된 변화(7일 밖)는 목록에서 빠지지만, 대분류 상세 그래프에는 계속 표시됩니다.
6. 최근 7일 안에 판단할 수 있는 날이 하나도 없으면(같은 요일 기록이 3번 미만) 정상·이상 판정 없이 **"판단 자료 부족"**을 보여줍니다.
7. 같은 날짜 파일을 **덮어쓰면** 그 날짜의 운영 상황 기록이 지워지고 새 숫자로 **다시 판정**합니다.

---

## 6. 매번 새로 계산됩니다

판정 결과는 저장하지 않고, 화면을 열 때마다 저장된 매출 기록 전부로 다시 계산합니다. 그래서:

- 파일을 새로 올리면 기록이 늘어 **평소 기준이 자동으로 갱신**됩니다. 이전 날짜의 판정도 새 기준으로 바뀔 수 있습니다.
- 올린 숫자를 덮어써도 따로 계산을 다시 돌릴 필요가 없습니다.
- 대분류 수와 기록이 많지 않아(대분류 약 20~30개 × 날짜 수백 개) 매번 계산해도 충분히 빠릅니다. 기록이 아주 많아지면 이 방식은 다시 검토합니다.

## 7. 이 방식의 성질과 한계

**가상 데이터 시뮬레이션** (대분류 15개, 평소 흔들림이 일정한 값):

| 평소 흔들림 | 기록 4번일 때 정상인데 뜨는 경고 | |
|---|---|---|
| 15% | 하루 약 0.1건 | 평소에 매우 안정적인 대분류 |
| 25% | 하루 약 0.9건 | 보통 |
| 35% | 하루 약 1.5건 | 흔들림이 큰 대분류 |

- 평소의 **2.5배**로 뛴 진짜 급증은 거의 100%(99.9%) 잡혔고, 1.6배는 약 65%였습니다.
- 기록이 쌓이면(6번 → 10번) 정상인데 뜨는 경고가 줄어듭니다. (25% 흔들림 기준 하루 0.56건 → 0.39건)

**알고 계실 한계**

- **연휴·행사·날씨:** 같은 요일끼리만 비교하므로 연휴나 장날(3·8일)의 영향은 반영하지 않습니다. 평소와 크게 달랐던 연휴 자체가 "변화가 큰 날"로 올라올 수 있고, 그 날이 이후 평소 기록에 섞이면 기준이 조금 흔들립니다.
- **하루 한 건 판정:** 대분류 수가 많으면 우연히 걸리는 경고가 있을 수 있습니다. "정상"이라고 기록하는 것은 이를 걸러내는 방법입니다.
- **기록이 적은 초반:** 3~5번일 때는 평소 중간값이 불안정합니다. 참고용으로 보시는 것이 안전합니다.
- **옛 자료의 영향:** 쌓인 기록을 전부 쓰므로 가게 상황이 크게 바뀌면(상권·메뉴 변화) 옛 기록이 평소를 왜곡할 수 있습니다. 반년쯤 쌓이면 최근 기간만 쓸지 검토합니다.
- **임계값은 가상 데이터 기준:** `점수 3`, `5,000원` 같은 값은 가상 데이터로 정한 초기값입니다. 실제 파일이 쌓이면 다시 조정합니다. (PRD 미정 7번의 남은 부분)

## 7-1. 이어지는 변화와 0원이 많은 분류 (추가 방식)

위의 하루 비교는 **하루짜리 큰 변화**에 강하지만 급감·품절, 며칠 이어지는 변화, 0원이 많은 분류의 안 팔림은 거의 놓칩니다. 그래서 기록이 **28일 이상** 쌓이면 [backend/app/detection.py](../backend/app/detection.py) 가 함께 판단합니다. 같은 칸을 두 방법이 모두 알리면 위의 하루 비교를 남깁니다. 쉬운 설명과 따라 해 볼 수 있는 예시는 [stats-guide.md](stats-guide.md) 4장, 시연 데이터 평가는 [lab.md](lab.md)에 있습니다.

| 분류 종류 (팔린 날 비율) | 방법 |
|---|---|
| 거의 매일 팔림 (90% 이상) | 요일 효과를 뺀 점수로 **Shewhart**(하루 점수 ≥ c, 5,000원 이상) + **CUSUM**(누적 > h) |
| 0원이 많음 (15~90%) | ① 팔린 날 비율 CUSUM(h) ② 팔린 날 금액 (위와 같은 방법, 기록 15일부터) |
| 거의 안 팔림 (15% 미만) | 평소보다 많이 팔린 날만: 수량이 지금까지 최대보다 많고 평소의 2배 이상, 금액이 수량 많았던 날만큼, 차이가 최소 금액 이상 |
| 한 번도 안 팔림 | 판단하지 않음 |

- 값은 로그(금액 + 1,000)로 바꿔 봅니다. 요일 효과는 **앞선 기록**으로 구해 먼저 빼고(같은 요일 기록이 적으면 0쪽으로 당김), 평소 수준은 최근 84일의 중간값입니다.
- CUSUM: 점수를 ±4로 자른 뒤 허용치 0.5를 빼며 위·아래를 따로 누적하고, 기준을 넘으면 알리고 0으로 되돌립니다.
- 같은 시각까지의 매출끼리만 비교합니다. 업로드가 없는 날은 건너뛰므로 "며칠째"는 올린 날 기준입니다.
- **휴일은 아직 반영하지 않습니다.** (시연 데이터 평가 도구는 알려진 휴일을 건너뛰지만 앱에는 휴일표가 없습니다. 연휴가 알림으로 올라올 수 있습니다)
- 알림 종류: `daily`(하루 점수) · `trend`(이어지는 변화) · `streak`(팔린 날 비율이 바뀜) · `big_sale`(거의 안 팔리는 분류가 많이 팔림). 화면에는 `daily`가 아닌 것만 한 줄 설명을 붙입니다.

### 민감도 (설정 화면)

| 민감도 | 하루 비교 점수 | 매일 팔림 (Shewhart, CUSUM) | 팔린 날 비율 CUSUM | 0원 많음 금액 (Shewhart, CUSUM) | 거의 안 팔림 최소 금액 |
|---|---|---|---|---|---|
| 낮음 | 4.0 | 4.0 / 8.0 | 5.0 | 4.0 / 8.0 | 5,000원 |
| **보통 (기본)** | 3.0 | 4.0 / 5.0 | 4.0 | 4.0 / 5.0 | 3,000원 |
| 높음 | 2.5 | 3.0 / 4.0 | 3.0 | 3.0 / 4.0 | 2,000원 |

값은 `detection.py`의 `LEVELS`에 있고, 선택은 DB의 `app_settings` 테이블에 저장됩니다(없으면 보통).

**시연 데이터(가짜)에서의 결과** — 현재 방식만 쓸 때와 보통 단계 비교. 변화의 크기·기간은 제가 정한 값이며 실제 가게의 정확도가 아닙니다.

| | 현재 | 보통 |
|---|---|---|
| 평범한 날 한 달(30일) 알림 | 11.9건 | 14.9건 |
| 하루짜리 급증 / 급감 / 품절을 그날 알림 | 83% / 9% / 8% | 85% / 44% / 25% |
| 매일 팔림, 28일 이어지는 ×0.6 / ×0.8 | 12% / 5% | 64% / 49% |
| 0원 많음, 28일 안 팔림 | 1% | 91% |

## 8. 조정할 수 있는 값

모두 [backend/app/anomalies.py](../backend/app/anomalies.py) 맨 위에 있습니다.

| 이름 | 현재 값 | 뜻 |
|---|---|---|
| `MIN_SAME_WEEKDAY_DAYS` | 3 | 판단에 필요한 같은 요일 기록 수 (홈의 비교와 같은 기준) |
| `RECENT_DAYS` | 7 | 홈 목록에 올리는 기간(일) |

## 11. AI 점검의 우선순위 (홈 "오늘의 점검")

"확인할 사항"이 여러 개일 때 **무엇을 먼저 확인할지**는 AI가 아니라 코드가 점수로 정합니다. (구현: [backend/app/ai/priority.py](../backend/app/ai/priority.py))

| 후보 | 조건 |
|---|---|
| 대분류 변화 | 이 문서 3~5장의 "판매 변화가 큰 날" 중, 최근 7일 안에서 아직 운영 상황을 기록하지 않은 것 |
| 총매출 | 총매출 분석에서 탐지 기준(p값 0.05 미만)을 넘은 경우. 점포 전체 기록이 없을 때만 |
| 집중 관리 식품군 | 최근 같은 요일 4번의 과거 관측 범위(최솟값~최댓값)를 벗어난 경우 (약한 신호) |

```
priority = 0.5 × base + 0.3 × impact + 0.2 × recency
base    = min(|탐지 점수|, 10) ÷ 10     (총매출 0.9, 식품군 0.4, 평소 한 번도 안 팔리던 분류가 팔린 경우 0.6)
impact  = min(|금액 − 기준| ÷ 총매출(총매출 항목은 기준 금액), 0.5) ÷ 0.5
recency = 1 ÷ (1 + 0.25 × 며칠 전)      (오늘 1.0, 하루 전 0.8, 이틀 전 0.67 …)
```

- **priority가 0.35 이상**인 후보만 올리고, 점수가 높은 순(동점이면 금액 차이가 큰 순, 이름순)으로 **상위 2개**까지입니다.
- **후보가 없으면 AI를 호출하지 않고** "오늘은 우선 확인할 변화가 없어요"를 보여줍니다. 자료가 부족하면 "비교할 기록이 아직 부족해요".
- 위 숫자는 **초기값**입니다. 실제 데이터로 점검이 너무 많거나 적게 뜨는지 보고 조정합니다. 상수는 `priority.py` 맨 위에 모여 있습니다.
- AI는 이 계산에 관여하지 않습니다. 고른 항목의 숫자(표시용 문자열)를 받아 읽기 쉬운 문장으로 정리할 뿐입니다.
